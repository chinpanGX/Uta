# プロデュース(育成)

## 目的

週ごとの行動選択と、レッスン・試験のカードバトルでパラメータを伸ばし、最終評価と報酬を得る育成ループの基礎部分を、サーバー権威で実装する。

参考作品の育成モードの**構造**を調査して決めた。名称は Uta の仮称([ADR 0001](../decisions/0001-ip-policy.md))。カードバトル部分は [lesson-card.md](lesson-card.md)、育成アイドル・サポートカードは [idol-support.md](idol-support.md)。

## 凡例

- **[確認]** 参考作品の攻略情報で裏取りした構造・数値
- **[決定]** Uta で決めたこと
- **[Uta案]** 実装方針の提案(まだ決定ではない)

数値は参考作品の値を**初期値**として使い、自動プレイでのバランス調整で差し替える前提。

## 完了条件(基礎部分)

- [ ] 育成開始 → 週の行動 → レッスン・試験 → 最終評価・報酬付与 が サーバー経由で動く
- [ ] 結果の確定・乱数はすべてサーバー。クライアントは入力と表示に加え、共有ドメインで使用可否の判定と予測の表示まで([ADR 0008](../decisions/0008-shared-domain-and-onion.md))
- [ ] 中断・再開ができる(状態がサーバーに保存されている)
- [ ] 同一シード+同一操作列で結果が再現できる

## 決まっていること

- サーバー権威([CLAUDE.md](../../../CLAUDE.md))
- 通信は MagicOnion の Unary([ADR 0002](../decisions/0002-magiconion.md))
- 3Dライブとは接続しない([ADR 0003](../decisions/0003-defer-3d-live.md))
- 参照するのは参考作品の基本シナリオ1つ。プランは感性・理論・共通の3つ。第3のプラン(指針を切り替える型)は実装しない [決定]
- 週構成・行動・レッスン設定は、コードに埋め込まずマスタで定義する [決定]

## 1. 全体フロー

```
編成(育成アイドル + サポートカード6枚)
  → プロデュース開始
  → 週ごとの行動選択(レッスン / 授業 / 支給 / おでかけ / 相談 / 休む)
  → 仕上げレッスン → 中間試験
  → 週ごとの行動選択
  → 仕上げレッスン → 最終試験
  → 最終評価・報酬
```

- 育成の土台は、プロデュース中に増えていくデッキでのカードバトル(デッキ構築型)。[確認]
- 編成の詳細は [idol-support.md](idol-support.md)。

## 2. 用語(仮称)

| 仮称 | 意味 |
|---|---|
| パラメータ | 歌唱 / 律動 / 表現 の3種 |
| 育成アイドル | 育成対象のキャラカード |
| 育成pt | プロデュース中だけ使うポイント。相談・おでかけで払う |
| ドリンク | レッスン・試験中に使う消費アイテム |
| 育成アイテム | プロデュース中ずっと効果を持つアイテム |
| 特別レッスン | 確率で発生する、目標が高く上昇量も大きいレッスン |
| 仕上げレッスン | 試験直前の週のレッスン |
| 審査比率 | アイドルごとの3パラメータの比率。試験のターン割り振りとスコアボーナスに使う |
| 信頼度 | アイドルごとの永続レベル。試験のスコアボーナスなどが増える |
| プレイヤーLv | アカウント単位のレベル。カードや機能が解放される |
| 不調カード | 授業などのコストとしてデッキに入る、効果のないカード |

### 3.1 週構成のマスタ [決定]

### 3.3 行動 [確認]

| 行動 | 効果 |
|---|---|
| 授業 | 体力などを払ってパラメータ上昇+スキルカード1枚(3.4) |
| 支給 | 育成pt、スキルカード1枚、ドリンク1つ |
| おでかけ | 育成ptを払って体力回復(最大体力の10〜60%)。選択肢によりドリンク、カードの獲得・強化・削除・チェンジも |
| 相談 | 育成ptでスキルカード4種・ドリンク4種と交換(50〜200、1つは30%引き)。強化と削除は1回の相談で各1回、費用は使うたびに100から25ずつ上がる |
| 休む | 最大体力の70%回復(切り捨て)。仕上げと試験の週は選べず、体力が減っているときのみ |

- 支給の育成pt(上級): 3・6週 95〜105、9・13週 145〜155、16週 0。初級・中級は約40〜60。
- おでかけは5つのイベントのグループから1つ。選択肢ごとに「コスト(0 / 50 / 100、または不調カード1枚)」「回復する割合」「追加の効果」が決まっている。

- 中級11週は、5つのイベントから1つがランダムで選ばれ、そのうち1つは通常レッスンに変わる。

### 3.5 スキルカードの獲得 [確認]

- レッスンのクリア報酬、授業、支給、おでかけ、相談などで獲得する。選択肢から1枚選ぶ。
- 選択肢は基本3枚。アイテムなどで増えることがある。
- 提示されるのは、育成アイドルのおすすめ効果に関係するカードだけ。共通カードや単純なパラメータ上昇だけのカードは提示されない。
- 再抽選: 選択肢をまとめて引き直せる。回数はプレイヤーLv10で+1、信頼度Lv5・Lv10で各+1、覚醒で増えることもある。
- 除去: 選択肢の1枚を消し、そのプロデュース中は出なくする。プレイヤーLv65で+1など。
- 選択肢のレアリティの出やすさ → 3.10(Uta で決める)

### 3.6 ドリンク [確認]

- 所持上限3つ。いつでも捨てられる。
- 使えるのはレッスン・試験中のみ。ターンもスキルカード使用数も消費しない。

## 4. レッスン

### 4.1 通常レッスン [確認]

- 終了条件: 規定ターン数の経過、またはパーフェクト目標への到達。
- クリア目標に届かなくてもパラメータは上がる。
- クリア目標を超えたら、クリア報酬(育成pt、スキルカード1枚、ランダムでドリンク)。
- パーフェクトで終了したら、クリア報酬に加えて「残りターン数×2」の体力回復。
- 特別レッスンは確率で発生する。1週目のレッスンと、授業から変わったレッスンは特別にならない。基本発生率は10%と考えられている(推定)。実際の発生率は、基本発生率+サポートカード・アイドルのアビリティの合計。

ターン数は感性 / 理論。目標は「クリア(パーフェクト)」。

| 難易度 | 週 | ターン | 通常 | 特別 |
|---|---|---|---|---|
| 初級 | 1 | 5 / 6 | 25(50) | なし |
| | 3 | 5 / 6 | 25(50) | 40(80) |
| | 9, 10 | 6 / 7 | 40(80) | 70(140) |
| 中級 | 1 | 5 / 6 | 30(60) | なし |
| | 4 | 5 / 6 | 30(60) | 45(90) |
| | 10 | 6 / 7 | 55(110) | 85(170) |
| | 11(授業から変化) | 6 / 7 | 45(90) | なし |
| | 12 | 6 / 7 | 60(120) | 100(200) |
| | 13 | 6 / 7 | 75(150) | 110(220) |
| 上級 | 5 | 5 / 6 | 30(60) | 45(90) |
| | 11 | 6 / 7 | 55(110) | 85(170) |
| | 14 | 6 / 7 | 60(120) | 100(200) |
| | 15 | 6 / 7 | 75(150) | 110(220) |

### 4.2 仕上げレッスン

- パラメータを1つ選ぶ点、クリア・パーフェクトの扱いは通常レッスンと同じ。[確認]
- クリア目標を超えた分は「仕上げボーナス」として全パラメータのレッスン扱いになり、上がった量を3等分して各パラメータに振り分ける。[確認] 余りは、次の試験の審査比率で1番目のパラメータに足す。[決定]
- 終了後、最大体力の70%(四捨五入)を回復する。[確認]

| 難易度 | 中間前(週 / ターン / クリア / パーフェクト) | 最終前 |
|---|---|---|
| 初級 | 5週 / 9・9 / 75 / 300 | 12週 / 10・9 / 100 / 400 |
| 中級 | 6週 / 9・9 / 90 / 360 | 15週 / 12・11 / 165 / 600 |
| 上級 | 7週 / 9・9 / 90 / 360 | 17週 / 12・11 / 165 / 600 |

## 5. 試験

### 5.1 ルール [確認]

- NPC5人とのスコア勝負。4位以下は不合格で、プロデュース終了。
- 再挑戦は、中間と最終を合わせて1回のプロデュースにつき3回まで。
- ターン数: 中間9、最終は感性12・理論11。初級・中級の中間は、スコア900(初級)/1800(中級)到達でも終了。
- 各ターンにパラメータがランダムに割り振られる。審査比率が高いパラメータほど多く割り振られる。
- 最後の3ターンは固定で、審査比率の3番目 → 2番目 → 1番目の順(最終ターンが1番目)。
- 最初のターンは基本的に1番目のパラメータ。1番目の比率が45%未満のアイドルは、1〜2割の確率で2番目になる。

ターン割り振り(1番 / 2番 / 3番のターン数):

| 審査比率 | 中間(9) | 最終・感性(12) | 最終・理論(11) |
|---|---|---|---|
| 40 / 33 / 27% | 4 / 3 / 2 | 5 / 4 / 3 | 5 / 3 / 3 |
| 45 / 40 / 15% | 4 / 3 / 2 | 6 / 4 / 2 | 5 / 4 / 2 |
| 50 / 30 / 20% | 5 / 2 / 2 | 6 / 3 / 3 | 5 / 3 / 3 |
| 60 / 23 / 17% | 5 / 2 / 2 | 7 / 3 / 2 | 6 / 3 / 2 |

順位報酬:

| 順位 | 中間(パラメータ / 育成pt) | 最終(パラメータ) |
|---|---|---|
| 1位 | 全+20 / 125 | 全+30 |
| 2位 | 全+10 / 100 | 全+20 |
| 3位 | 全+5 / 75 | 全+10 |

中間試験に合格すると、育成アイテムも1つ獲得する。

信頼度によるスコアボーナス増加(Lv1〜10): 0 / 5 / 10 / 15 / 15 / 20 / 30 / 40 / 50 / 50%

### 5.2 スコアボーナス [決定]

参考作品の式は公開されていないため、Uta 独自の式を使う。

```
スコアボーナス(%)     = floor( a × そのターンのパラメータの値 ) + b[審査比率の順位]
最終スコアボーナス(%) = floor( スコアボーナス × (100 + 信頼度補正%) / 100 )
スコア上昇値          = ceil( 最終パラメータ上昇値 × 最終スコアボーナス / 100 )
```

- 試験中のパラメータ上昇はすべてスコアに変換する(カード、好印象によるターン終了時の上昇、持続効果を含む)。
- 計算はすべて整数(%を整数で持つ)。

| 係数 | 初期値 |
|---|---|
| a | 0.225(マスタ上は 225/1000) |
| b[1番] / b[2番] / b[3番] | 190 / 150 / 120 |
| 信頼度補正 | 0〜50%(5.1の表) |

計算例(信頼度補正0%):

| パラメータの値 | 1番 | 2番 | 3番 |
|---|---|---|---|
| 300 | 257% | 217% | 187% |
| 600 | 325% | 285% | 255% |
| 1000 | 415% | 375% | 345% |
| 1500 | 527% | 487% | 457% |

### 5.3 NPCのスコア [決定(仮の値)]

- 試験ごとに基準スコア R を置き、NPC1〜5を R の 80% / 65% / 50% / 35% / 20% にする。端数は切り捨て。
- R: 中間は早期終了スコア(初級900、中級1800)。最終は中間の2.5倍を仮置き。上級は中級と同じ R に、育成アイテムの「ライバルのスコア増加」を上乗せする。
- 同点はプレイヤーを上の順位とする。NPCのスコアに乱数は入れない。

| 試験 | R | NPC1 | NPC2 | NPC3 | NPC4 | NPC5 |
|---|---|---|---|---|---|---|
| 初級 中間 | 900 | 720 | 585 | 450 | 315 | 180 |
| 初級 最終 | 2,250 | 1,800 | 1,462 | 1,125 | 787 | 450 |
| 中級・上級 中間 | 1,800 | 1,440 | 1,170 | 900 | 630 | 360 |
| 中級・上級 最終 | 4,500 | 3,600 | 2,925 | 2,250 | 1,575 | 900 |

## 6. 最終評価 [確認]

```
評価値     = パラメータ分 + 最終試験の順位分 + 最終試験のスコア分
パラメータ分 = floor( (歌唱 + 律動 + 表現) × 2.3 )
順位分      = 1位 1700 / 2位 900 / 3位 500 / 4位以下 0
スコア分    = floor( スコア × 倍率 + 固定値 )
```

| スコア | 倍率 | 固定値 |
|---|---|---|
| 0〜5,000 | 0.30 | 0 |
| 5,001〜10,000 | 0.15 | 750 |
| 10,001〜20,000 | 0.08 | 1,450 |
| 20,001〜30,000 | 0.04 | 2,250 |
| 30,001〜40,000 | 0.02 | 2,850 |
| 40,001〜199,999 | 0.01 | 3,250 |
| 200,000〜 | 0 | 5,250(上限) |

| 評価値 | 0 | 1,000 | 2,000 | 3,000 | 4,500 | 6,000 | 8,000 | 10,000 | 11,500 | 13,000 | 14,500 | 16,000 | 18,000 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| ランク | F | E | D | C | C+ | B | B+ | A | A+ | S | S+ | SS | SS+ |

- SS+ が上限。
- [Uta案] スコア分の区切りは、5.2・5.3 のスコア水準に合わせて調整する。
- 評価の計算は `Uta.Domain` に置き、評価の見込みの表示にも使う。式の小数（2.3、0.30 など）は千分率の整数にして計算する [決定。2026-10-28。[api-design.md](../architecture/api-design.md) 4章]

### 6.1 報酬 [決定。2026-10-28／数値は仮]

最終評価のランクに応じて、サーバーが付与する（付与はサーバー専用。[api-design.md](../architecture/api-design.md) 4章）。

| 報酬 | 使い道 |
|---|---|
| ガチャ通貨 | ガチャ([gacha.md](gacha.md)) |
| ゴールド | 育成アイドルのトレーニング、サポートカードのレベルアップ([idol-support.md](idol-support.md)) |
| プレイヤー経験値 | プレイヤーLv(7章) |

- ランクごとの量はマスタで持つ。仮の値はガチャ通貨で C 100 / B 200 / A 300 / S 500(単発 250 なので、1回のプロデュースで 0.5〜2 回分)。ゴールド・経験値の量は実装するときに仮の値を置く
- 放棄・破棄したプロデュースには報酬を付けない([api-design.md](../architecture/api-design.md) 5章)
- ランク以外の報酬(初回クリアなど)は作らない

## 7. プレイヤーLv [確認]

- プロデュース1回の経験値: 初級 10〜20、中級・上級 30〜50(中間不合格 / 最終不合格 / 最終合格で変わる)。
- 必要経験値はレベルごとの表で持つ(例: Lv2まで40、Lv10まで累計6,130、Lv20まで累計34,530。Lv55以降は1レベル70,000)。
- 機能の解放: Lv5 相談での強化、Lv10 再抽選+1、Lv15 相談での削除、Lv65 除去+1。
- カード・ドリンクもレベルで解放される(カードの `unlockLv`)。
- [Uta案] 参考作品は経験値の大半を課題・実績の報酬で得る。Uta にはその仕組みが無いので、プロデュース報酬の経験値を増やすか、必要経験値を減らす。

## 8. Uta で決めること(参考作品で未公開)

| 項目 | 案 |
|---|---|

## 10. 乱数・操作の記録・サーバー状態

### 10.0 前提 [決定]

- サーバー権威。結果の確定は常にサーバー。クライアントはシードと乱数を持たず、共有ドメインで使用可否の判定と予測の表示までを行う。乱数が絡む結果は予測しない([ADR 0008](../decisions/0008-shared-domain-and-onion.md))
- 乱数は `xoshiro256**`。`System.Random` は使わない。シードはサーバーが生成する([repository-layout.md](../architecture/repository-layout.md) 10.3)
- `float` / `double` を使わない([lesson-card.md](lesson-card.md) 9.6)
- セッションは検索用の列と、状態を丸ごと入れた1列(MessagePack の `bytea`)に分け、バージョン列で楽観ロックをかける([ADR 0010](../decisions/0010-database.md)、[api-design.md](../architecture/api-design.md) 3章)
- 操作の RPC は `ChooseWeekAction`(週の行動)と `ExecuteLessonAction`(レッスン・試験の操作)に分ける。再送は `x-request-id` + `last_responses` に任せる([api-design.md](../architecture/api-design.md) 1章、[server-foundation](../architecture/server-foundation.md))
- 同じシードと同じ操作列で、同じ結果を再現できる(完了条件)
- 1ユーザーにつき進行中のセッションは1つ [決定。[api-design.md](../architecture/api-design.md) 3章]
- 中断(アプリの終了)は期限なしで再開できる。放棄は明示の操作で、報酬なし。**開始したときとアプリのバージョン(または状態の形式のバージョン)が違えば、進行中のセッションを破棄する**(報酬なし) [決定。2026-10-28。[api-design.md](../architecture/api-design.md) 5章]
- 状態の中身・乱数・操作の記録はこの章が正。セッションの検索用の列と、中断・放棄・破棄の流れは [api-design.md](../architecture/api-design.md) 3.1・5章が正

以下 10.1〜10.6 は [決定]。2026-10-28 に決めた。10.7 は未決。

### 10.1 処理の単位: 入力待ちから入力待ちまで

- サーバーは1回の操作を受けると、**次にプレイヤーの入力が要る地点(入力待ち)まで**を1回で処理し、その状態を保存して返す。
  - 例: カードを使う → 効果の処理 → (使用数が尽きたら)ターン終了 → 次のターン開始・ドロー → 入力待ち
  - 例: 週の行動を選ぶ → サポートイベント → 行動の結果 → スキルカードの選択肢の提示 → 入力待ち
- 保存される状態は、常にどこかの入力待ち。途中再開は「最後の入力待ちから続ける」だけになり、処理の途中を保存する仕組みは要らない。
- 乱数で決まる提示内容(授業の上昇パラメータ、相談の品ぞろえ、カードの選択肢など)は、**提示する前に引いて状態に保存する**。再接続や `GetState` で引き直さない(リセマラの防止)。

### 10.2 乱数ストリーム

セッションのシード(マスターシード)から、用途と場面ごとに独立したストリームを作る。

| ストリーム | キー | 使う場面 |
|---|---|---|
| `Scenario` | なし(1本) | 上級の週パターン、中級11週のイベント(3.2、3.4) |
| `Week` | 週番号 | 特別レッスンの判定、授業の上昇パラメータと確率分岐、おでかけのイベント、相談の品ぞろえと割引、支給の育成pt、サポートイベントの発生、クリア報酬のドリンク |
| `Offer` | 週番号 | スキルカードの選択肢の抽選と再抽選(3.5) |
| `Lesson` | 週番号 + 挑戦回数 | 山札のシャッフルと再シャッフル、不調カードの生成位置、ランダムな効果、スキルカードサポート、試験の審査ターン |

- マスターシード: 64 ビット。プロデュース開始時にサーバーが暗号用の乱数で生成する(暗号用の乱数を使う点は [repository-layout.md](../architecture/repository-layout.md) 10.3 の推測のまま)。
- ストリームの初期化: `(マスターシード, ストリームの種類, 週番号, 挑戦回数)` を SplitMix64 で混ぜて 64 ビットの値を作り、それを SplitMix64 で4回伸ばして `xoshiro256**` の 256 ビットの状態にする(xoshiro の作者が推奨する初期化の方法)。混ぜ方の細部は実装時に固定し、テストベクタで守る。
- 1本のストリームにしない理由:
  - あるレッスンで引く回数が変わっても(ドロー効果のあるカードを足すなど)、後の週の結果がずれない。自動プレイでのバランス比較と、不具合の切り分けがしやすい
  - 試験の再挑戦は挑戦回数がキーに入るので、山札の並びが前回と変わる(並びを覚えて再挑戦する攻略を防ぐ)
  - 保存するのは、使用中のストリームの状態だけで済む
- `Offer` を `Week` から分けるのは、カードの選択肢の重みを調整しても、ほかの週の判定がずれないようにするため。

乱数の取り出し方(`Uta.Domain` に置き、同じコードで固定する):

| 操作 | 方法 |
|---|---|
| `NextInt(n)`(0 以上 n 未満) | 64 ビットの値を引き、`(2^64 − n) mod n` 未満なら引き直す(棄却法)。残りを `mod n`。偏りが出ず、64 ビットの演算だけで済む |
| 確率の判定 | 確率は万分率の整数。`NextInt(10000) < 率`。**判定する場面では、率が 0% や 100% でも1回引く**(マスタの値を変えても、引く回数が変わらないようにする) |
| 範囲 `[min, max]` | `min + NextInt(max − min + 1)` |
| 重み付きの抽選 | 重みの合計 `W` に対して `NextInt(W)`。候補はマスタの ID の昇順に並べて累積する |
| シャッフル | Fisher–Yates。末尾から、`i` 番目と `NextInt(i + 1)` 番目を入れ替える |

### 10.3 乱数を引く順番

決まった順番で引く。どこで何回引いたかは、状態と操作列から一意に決まる。

**プロデュース開始時**(`Scenario`)

1. 上級なら週パターン(A / B / C)
2. 中級なら11週のイベント

**週の開始時(提示の前)**(`Week`。前の週の処理を終えた同じ要求の中で行う)

1. 特別レッスンの判定(対象のレッスン週だけ。率は基本発生率+アビリティの合計)
2. 授業: 選択肢の順に、上昇するパラメータ
3. おでかけ: イベント
4. 相談: スキルカード4種、ドリンク4種、割引の対象

その週に出ない行動の分は引かない。

**行動を選んだ後**(`Week`)

1. サポートイベント(行動の前): 編成の順に、各カードの発生判定
2. 行動の確率分岐(授業の「40%で110」など)、支給の育成pt
3. サポートイベント(行動の後): 編成の順に、各カードの発生判定
4. スキルカードの選択肢(`Offer`): 枠の順に、レアリティを重みで引き、そのレアリティの候補から1枚を引く。同じ選択肢の中での重複と、除去したカードは候補から外す。再抽選は同じストリームの続きから引く

**レッスン・試験の開始時**(`Lesson`。[lesson-card.md](lesson-card.md) 10章の L1・L2)

1. 試験なら審査ターン: 先頭のターンの判定(1番目の比率が45%未満のときだけ)→ 最後の3ターンと先頭を除いた残りのターンをシャッフル
2. L1 の「レッスン開始時」効果の中の乱数(効果の記載順)
3. L2: 開始時手札のカードが5枚を超えるなら、そのカードの組をシャッフルして先頭5枚を手札へ
4. L2: 残りのカード(超えた分を含む)を、カードのインスタンス ID の昇順に並べてからシャッフルし、山札にする

**ターン中**(`Lesson`。lesson-card.md 10章の順)

- T3・T5・T7・P6・E2 などの効果の中の乱数は、効果を処理する順に引く
- T4 のドローや効果のドローで山札が空になったら、その時点で捨札をシャッフルする(捨札は入った順に並べてからシャッフル)
- 山札のランダムな位置への生成は `NextInt(山札の枚数 + 1)`(0 が一番上)
- スキルカードサポート(フェーズ5以降): T4 の直後に、編成の順で発生判定 → 発生したら対象の手札を `NextInt(対象の枚数)` で選ぶ。タイミングは仮

**レッスンの後**: クリア報酬のドリンク(`Week`)→ スキルカードの選択肢(`Offer`)

### 10.4 操作の記録

受け付けた操作だけを、受け付けた順に記録する。拒否した操作は記録しない。

| 局面 | 操作 | 引数 |
|---|---|---|
| 週 | 行動を選ぶ | 行動の枠番号、選択肢の番号(授業・おでかけ)、パラメータ(レッスン) |
| 相談 | 交換する / 強化する / 削除する / 終える | 品の番号 / カードのインスタンス ID |
| カードの選択肢 | 選ぶ / 再抽選 / 除去 / 受け取らない | 選択肢の番号 |
| ドリンク | 捨てる | ドリンクの枠番号 |
| 試験 | 再挑戦する / しない | — |
| レッスン・試験 | カードを使う | カードのインスタンス ID |
| レッスン・試験 | ドリンクを使う | ドリンクの枠番号 |
| レッスン・試験 | スキップ | — |

1件の記録: `操作番号(0 から連番)`、`操作の種類(enum)`、`週番号`、`挑戦回数`、`ターン番号`、`引数(int × 2)`。

- **カードはインスタンス ID で指す**。手札の位置では指さない(表示の並びに左右されない)。インスタンス ID はセッションの中だけの連番の `int`(初期デッキはマスタの順に 1 から、以降は入手順)。セッションの外には出ないので ULID にしない([repository-layout.md](../architecture/repository-layout.md) 10.1 の「サーバーが発行する ID」には当たらない、という整理)
- **要求には次の操作番号を入れる**。サーバーの番号と違えば拒否し、クライアントは `GetState` で取り直す。同じターンにカードとドリンクを続けて使うと、ターン番号だけでは古い要求と新しい要求を区別できないため([api-design.md](../architecture/api-design.md) 1章にも反映)
- 記録は状態の1列(10.5)の中に持つ。1回のプロデュースで数百件・数 KB の見込み(推測)で、ADR 0010 の「1ターンの読み書きが1行」を変えずに済む。調査で SQL から見たくなったら、別テーブルに追記する形に移す

### 10.5 保存する状態(途中再開)

状態の1列に入れるもの。検索用の列(ユーザー、状態、週、ターン、開始時のアプリのバージョン、状態の形式のバージョン、楽観ロックのバージョン)は ADR 0010・[api-design.md](../architecture/api-design.md) 3.1 のとおり。

| 区分 | 内容 |
|---|---|
| 形式 | 状態の形式のバージョン |
| 開始時の入力 | セッション ID、ユーザー ID、シナリオ・難易度、**育成アイドルとサポートカード6枚の開始時点の性能**(トレーニング・覚醒・レベル・上限解放。レンタル枠を含む)、マスタの版、ルールの版、マスターシード |
| 乱数 | 使用中のストリームごとに、種類・キーと `xoshiro256**` の状態(64 ビット × 4)、引いた回数(調査用) |
| 進行 | 局面(週の選択 / 相談中 / カードの選択肢 / レッスン / 試験 / 終了)、週番号、確定した週構成、その週に提示した内容(10.3 で引いたもの)、相談の残り回数と費用 |
| 育成 | パラメータ3種、体力・最大体力、育成pt、デッキ(インスタンス ID・カード ID・強化済みか)、ドリンク(最大3)、育成アイテム(残り回数)、再抽選・除去の残り回数、除去したカード、試験の再挑戦の残り回数、中間試験の結果、回数制限のあるアビリティの使用回数 |
| レッスン中だけ | レッスンの種類・挑戦回数・ターン・目標、試験なら審査ターンの列とスコア、山札(**並び順を含む**)・手札・捨札・除外、レッスン中強化のフラグ、元気、各ステータス(値・ターン数・初付与のフェーズ。lesson-card.md 11章)、上昇量増加のリスト、発動予約、持続効果、このターンの残り使用数 |
| 記録 | 操作の記録(10.4) |

- 開始時の性能を写して持つのは、プロデュース中にトレーニングなどをしても、進行中のセッションの結果を変えないため。
- `GetState` で返さないもの: マスターシード、ストリームの状態、**山札の並び順**(枚数と、並べ替えた中身だけを返す。PRD-08)、まだ提示していない乱数の結果。
- `Uta.Domain` は MessagePack に依存しない。保存の形はサーバーの `Infrastructure` で、共通の状態の型を包んで作る(ADR 0010 の「影響・リスク」、[repository-layout.md](../architecture/repository-layout.md) 6.1)。

### 10.6 再現の確かめ方

- 「開始時の入力+操作の記録」を最初から再生すると、保存した状態と一致する。これを `Uta.Domain` の単体テストで確かめる(lesson-card.md 15.7、repository-layout.md 10.4)。
- 比べやすいよう、状態から決まったハッシュを作る関数を用意する(順序が決まった項目だけから作る)。
- 再現を保証するのは、**マスタの版とルールの版が、開始時と同じ場合だけ**。版が変わったセッションは、再生の検証の対象から外す(アプリのバージョンが変わったセッションは破棄される。10.0)。
