# 育成アイドル・サポートカード

[プロデュース](produce.md)の編成に使うカード(育成アイドル、サポートカード)の仕様。入手は [ガチャ](gacha.md)。

参考作品の構造を調査して決めた。名称は Uta の仮称([ADR 0001](../decisions/0001-ip-policy.md))。

凡例: **[確認]** 参考作品で裏取りした構造・数値 / **[決定]** Uta で決めたこと / **[Uta案]** 提案

用語の定義は [glossary.md](../glossary.md) の「育成アイドル・ガチャ（仮称）」の表が正。このページには書かない。

数値は参考作品の値をマスタの初期値として使い、バランス調整で差し替えてよい([確認] の印の値。[ADR 0016](../decisions/0016-reference-game-values.md))。

MVP で作る範囲は 4章の「必須」([game-spec.md](../overview/game-spec.md) 最小実装範囲)。トレーニング・覚醒・サポートイベント・スキルカードサポート・レンタル枠は MVP では作らないが、仕様は残す。

## 1. 育成アイドル

### 1.1 位置づけ

- プロデュースで育てる対象。レアリティは R / SR / SSR。[確認]
- 参考作品は「アイドル個人と楽曲の組み合わせで1枚」で、同じアイドルでも楽曲ごとに別のカードになる。[確認]
- **Uta は楽曲の軸を持たない。育成アイドルは 1 キャラ 1 枚**(`idol_id` が 1 キャラ)[決定。2026-10-31]。かけら・覚醒・信頼度は `idol_id` ごとに持つ。楽曲は 3D ライブとともに保留([ADR 0003](../decisions/0003-defer-3d-live.md))

### 1.2 ステータス [確認]

| 項目 | 内容 |
|---|---|
| 体力 | 最大体力。トレーニング・覚醒などで増える |
| 初期パラメータ | 歌唱 / 律動 / 表現の初期値 |
| パラメータボーナス | パラメータごとの率。対応するレッスンの終了時に、上がった量 × ボーナス が**追加で**上がる(小数点以下切り捨て) |
| アビリティ | トレーニング・覚醒で解放される特殊効果(1.7) |
| 固有スキルカード | プロデュース開始時に持っている専用カード |
| 固有育成アイテム | プロデュース開始時に持っている専用アイテム(MVP では使わない) |
| プラン・おすすめ効果 | 感性(好調・集中)/ 理論(好印象・やる気) |

- プランによって、登場するスキルカード・ドリンク・育成アイテムの種類が変わる。共通のものはどのプランでも登場する。
- **パラメータボーナスの単位と計算** [決定。2026-10-31]: ボーナスは**千分率**の整数で持つ(8.5% → 85)。育成アイドルとサポートカード(アビリティ)のボーナスをパラメータごとに**合算してから**掛け、最後に 1 回だけ切り捨てる: `追加 = floor(上がった量 × 合算した千分率 / 1000)`。レッスンの後の処理の順は [produce.md](produce.md) 4.3
- 信頼度([glossary.md](../glossary.md))は MVP では使わない(0 固定。[produce.md](produce.md) 5.2)

### 1.3 初期デッキ

9枚。[確認]

| 内訳 | 枚数 |
|---|---|
| 全アイドル共通: F01×2、F02×1、F03×2([lesson-card](lesson-card.md) 14章) | 5 |
| 固有スキルカード | 1 |
| おすすめ効果ごとのカード(アクティブ1枚、メンタル2枚) | 3 |

おすすめ効果ごとの 3 枚 [決定。2026-10-31。参考作品からの推定を Uta の値として採る]。マスタ(育成アイドルのおすすめ効果)から引く:

| おすすめ効果 | アクティブ | メンタル |
|---|---|---|
| 好調 | S04 | S01×2 |
| 集中 | S03 | S02×2 |
| 好印象 | L04 | L01×2 |
| やる気 | L06 | L03×2 |

- 並び(カードのインスタンス ID の採番順。[produce.md](produce.md) 10.4): 共通 5 枚 → 固有 1 枚 → おすすめ 3 枚。各グループの中はカード ID の昇順。同じカードが複数あれば続けて振る [決定。2026-10-31]

### 1.4 審査比率

- アイドルごとに固定の、3パラメータの比率。試験のターン割り振りとスコアボーナスに使う([produce](produce.md) 5章)。[確認]
- 参考作品で見られる比率の型(1番 / 2番 / 3番): 40/33/27、45/40/15、50/30/20、60/23/17。[確認]
- **Uta のアイドルもこの 4 型から選ぶ** [決定。2026-10-31]。育成アイドルのマスタは「審査の型 ID」と「どのパラメータが 1 番・2 番・3 番か」を持ち、型ごとの比率と試験のターン割り振りは型のマスタで持つ([produce.md](produce.md) 5.1)

### 1.5 トレーニング(段階強化) [確認。MVP では作らない]

育成素材とゴールドを使う。6段階。

| 段階 | 主な強化内容 |
|---|---|
| 1 | 最大体力 または パラメータ |
| 2 | アビリティ解放 |
| 3 | 固有スキルカードの強化 |
| 4 | パラメータ |
| 5 | 最大体力 |
| 6 | アビリティ強化 |

必要素材(SSR):

| 段階 | 素材1 | 素材2 | 素材3(プラン別2種、各) | 素材4 | ゴールド |
|---|---|---|---|---|---|
| 1 | 300 | - | - | - | 5,000 |
| 2 | 700 | 250 | - | - | 10,000 |
| 3 | 1,200 | 750 | 30 | - | 30,000 |
| 4 | 2,400 | 1,250 | 150 | 1 | 50,000 |
| 5 | 3,600 | 2,000 | 300 | 2 | 100,000 |
| 6 | 4,600 | 2,500 | 600 | 5 | 150,000 |

- SR は SSR の0.6倍、R は0.4倍(素材4を除く)。素材4は SR で段階5に1、段階6に2、R は不要。[確認]。計算するとすべて整数になるので、マスタにはレアごとの値を直接持つ(倍率で計算しない)
- 素材3は、そのアイドルのプランの素材(感性用・理論用の 2 種のうち 1 種)を使う
- 段階3の「固有スキルカードの強化」は、固有スキルカードを強化版(+)に置き換えること([lesson-card.md](lesson-card.md) 12章)
- 段階ごとの強化量と、育成素材の入手手段は、トレーニングを作るときに決める(未決事項)

### 1.6 覚醒 [確認。MVP では作らない]

同じアイドルの「かけら」を使う。4段階。かけらはガチャの重複などで手に入る([gacha.md](gacha.md) 5章)。

| 段階 | 主な強化内容 | SSR / SR | R |
|---|---|---|---|
| 1 | 2つ目のアビリティ解放 | 50 | 25 |
| 2 | 固有育成アイテムの強化(強化版の定義は育成アイテムを作るときに決める) | 100 | 50 |
| 3 | パラメータボーナス強化 | 150 | 75 |
| 4 | 最大体力、2つ目のアビリティ強化 | 200 | 100 |

- 段階 4 の「アビリティ」は、参考作品では 3 つ目の解放。Uta は 1.7 の 2 枠だけにするので、2 つ目の強化に置き換えた [決定。2026-10-31]

### 1.7 アビリティ

| 枠 | 効果 | 解放したとき | 強化したとき |
|---|---|---|---|
| 1 | 全特別レッスン発生率 | トレーニング2 で +5% | トレーニング6 で +10% |
| 2 | スキルカード再抽選回数 | 覚醒1 で +1 | 覚醒4 で +2 |

- [Uta案] 初期実装はこの1パターンだけにする。
- 「全特別レッスン発生率」は、3 パラメータそれぞれの特別レッスン発生率に同じ値を足す([produce.md](produce.md) 10.3)
- どちらの枠もトレーニング・覚醒で解放されるので、MVP では発動しない

### 1.8 入手

- 基本はガチャ。[確認]
- **アカウントを作ったときに、R の育成アイドル全員を付与する** [決定。2026-10-31。[game-spec.md](../overview/game-spec.md)]
- 参考作品の「未所持のアイドルのかけらを100個集めると解放(SSR)」「最初のプロデュースで SSR を1人選んで獲得」[確認] は MVP では作らない

### 1.9 対象外 [決定]

- 別衣装・別楽曲のバリエーション、トレーニング7段階目、カードの見た目変更

## 2. サポートカード

### 2.1 位置づけと編成

- プロデュースに6枚編成する(自分のカード5枚+レンタル1枚)。[確認]
- レアリティは R / SR / SSR。[確認]
- タイプは 歌唱 / 律動 / 表現 / アシスト の4種。アシストは体力回復や相談の割引など特殊な能力。[確認]
- プラン区分(感性 / 理論 / 共通)を持つ。[確認]

編成のルール [決定。2026-10-31]:

- 自分のカードの枠は 5 つ。**0〜5 枚で開始できる**(空き枠を許す)
- 編成の順は、自分のカードの枠の順(1〜5)。プロデュース中の「編成の順」([produce.md](produce.md) 10.3)はこの順
- レンタル枠(2.6)は MVP では作らない。作るときは常に 6 番目(末尾)に置く
- タイプ(アシストを含む)による制限はない
- 検証は `StartAsync` で、次の順に行う。どれに当たっても `PRODUCE_INVALID_FORMATION`([produce.md](produce.md) API案):
  1. 育成アイドルを所持していない
  2. 所持IDが 6 個以上ある
  3. 所持IDが自分の所持でない(無い ID・他人の ID)
  4. 同じ所持IDが 2 回ある
  5. 同じカード ID のカードが 2 枚以上ある(所持IDが別でも)
  6. 育成アイドルのプランと違うプランのカードがある(プラン区分が共通のカードはどのアイドルでも選べる)
  7. `RentalCandidateId` が 0 でない(MVP はレンタル枠を作らない)。この項目だけ `PRODUCE_INVALID_ARGUMENT`
- 検証の置き場: 1〜4(所持の解決)はサーバーが DB を引いて行う。解決したカード(カード ID・プラン・レベル・上限解放回数)の列と育成アイドルを受けて、5・6 を `Uta.Domain` の関数で判定する。クライアントは所持一覧から同じ関数で編成の可否を表示する

### 2.2 レベルと上限解放 [確認]

| レア | 上限解放0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| R | 20 | 25 | 30 | 35 | 40 |
| SR | 30 | 35 | 40 | 45 | 50 |
| SSR | 40 | 45 | 50 | 55 | 60 |

- レベル上げには「サポート強化pt」と「ゴールド」を使う [決定。2026-10-31]。強化pt の最大レベルまでの累計は R 30,360 / SR 79,680 / SSR 207,700 [確認]。レベルごとの必要量(強化pt・ゴールド)はレアリティごとにマスタで持つ。
- 必要量の正は**マスタの行**(`SupportLevelCost`。6章)。行の初期値は次の式で作る [決定。2026-10-31]: Lv L → L+1 に要る強化pt は `基準 × L`(基準は R 39 / SR 65 / SSR 117)。ゴールドは強化pt と同じ量。最大レベルまでの累計は R 30,420 / SR 79,625 / SSR 207,090 で、上の確認値と少しずれるが受け入れる
- 上限解放の回数ごとの上限レベル(上の表)もマスタの行(`SupportLevelCap`。6章)で持つ
- 完凸(上限解放4回)には同じカードが5枚必要。上限解放に通貨や強化ptは要らない。
- 完凸後の重複 → 2.2.1・3章

### 2.2.1 所持の持ち方と上限解放の操作 [決定。2026-10-31]

- 所持しているサポートカードは、**1枚ずつ ULID(所持ID)で持つ**。ガチャで引くたびに1行増える。レベルと上限解放回数は所持IDごとに持つ([api-design.md](../architecture/api-design.md) 3章)。増えた行はレベル 1・上限解放 0(初期付与の 5 枚も同じ)
- この持ち方を選んだ理由: 同じカードは編成に 1 枚までなので、プレイヤーにとっての利点は小さい。それでも、サーバーが発行する ID(ULID)で所持品を持つことと、2 つの行をまたいで更新する RPC(上限解放)の技術検証の題材にするため、この形にする(ユーザーの判断。2026-10-31)。代わりの案(カード ID ごとに 1 行・引いたときに自動で上限解放)のほうが単純だが、検証の題材が減る
- **レベル上げ**は、所持ID と**目標のレベル**を指定して `LevelUpAsync` で確定する。今のレベルから目標までの必要量をまとめて払う。一部だけ上げることはしない。手順(1 つのトランザクション。最初に `players` の行をロックする: [api-design.md](../architecture/api-design.md) 3章):
  1. 所持IDが自分の所持でなければ `SUPPORT_NOT_OWNED`
  2. 目標が今のレベル以下、または上限解放で決まる上限を超えれば `SUPPORT_INVALID_TARGET_LEVEL`
  3. 必要量(強化pt・ゴールド)を `SupportLevelCost` の行から合計する
  4. `UPDATE players SET support_points = support_points - @p, gold = gold - @g WHERE player_id = @id AND support_points >= @p AND gold >= @g` の 1 文で払う。0 行なら残高を読み直し、強化pt が足りなければ `SUPPORT_NOT_ENOUGH_POINTS`、そうでなければ `PLAYER_NOT_ENOUGH_GOLD`(強化pt を先に見る)
  5. 所持IDの行のレベルを目標にする
- 上限解放は**手動**。プレイヤーが「解放するカード」と「素材にするカード」(同じカードIDの別の所持ID)を1枚ずつ選び、`LimitBreakAsync` で確定する。素材にしたカードは消え、解放するカードの上限解放回数が1増える
  - 手順(1 つのトランザクション。検証はこの順。最初に `players` の行をロックする: [api-design.md](../architecture/api-design.md) 3章):
    1. 解放するカードが自分の所持でなければ `SUPPORT_NOT_OWNED`
    2. 素材が解放するカードと同じ所持ID なら `SUPPORT_INVALID_MATERIAL`
    3. 素材を消す: `DELETE FROM player_support_cards WHERE support_card_uid = @m AND player_id = @id AND card_id = @c`。0 行(無い・他人の・別のカード)なら `SUPPORT_INVALID_MATERIAL`
    4. 解放する: `UPDATE player_support_cards SET limit_break = limit_break + 1 WHERE support_card_uid = @t AND player_id = @id AND limit_break < 4`。0 行なら `SUPPORT_MAX_LIMIT_BREAK`(トランザクションごと取り消すので、3 の削除も戻る)
  - 完凸した後も、同じカード ID の残りの所持ID(上限解放 0〜3 のもの)は消さずに残す [決定。2026-10-31]。素材にはできない(解放するカードが完凸のため)が、編成とレベル上げはできる。自動で強化pt に変換しないのは、レベルを上げた行の投資を確認なしに消さないため。強化pt に変換するのは、完凸の後にガチャで引いた分だけ(下)
  - 同時に同じ素材を使う要求が来ても、3・4 が 1 文の条件付きの更新なので、片方が 0 行になって失敗する。再送は `x-request-id` で冪等に扱う(基盤)
  - 素材のレベルに使った強化pt・ゴールドは戻らない。画面で素材のレベルが1より大きいときは確認ダイアログに出す
  - 上限解放4回のカードはそれ以上解放できない(`SUPPORT_MAX_LIMIT_BREAK`)。素材が解放するカードと同じ所持ID、別のカードID、他人の所持なら拒否する
  - 進行中のプロデュースに編成している所持IDも、解放・素材にできる。プロデュースは開始時の性能の写しを使い、セッションには所持IDではなく**カード ID・レベル・上限解放回数**を写す([produce.md](produce.md) 10.5)。素材で行が消えても、表示も結果も変わらない
- 完凸後の重複は、ガチャで引いた時点で変換する: 同じカードIDで上限解放4回の所持IDを1枚でも持っていれば、行を増やさずサポート強化pt に変換する(`DrawAsync` のトランザクション内。量は3章)。持っていなければ、上限解放の回数にかかわらず1行増やす。天井の交換(`ExchangeAsync`)で受け取ったときも同じ
- RPC・エラーは [api-design.md](../architecture/api-design.md) 1・2章

### 2.3 サポートアビリティ [確認]

6枠。レベルで解放・強化される。

| 枠 | 解放レベル(R / SR・SSR) | 内容の傾向 |
|---|---|---|
| 1 | 1 / 1 | 初期パラメータ・パラメータボーナス・最大体力など開始時の効果 |
| 2 | 1 / 1 | カードごとに異なる |
| 3 | 2 / 2 | 全カード共通:「このカードのスキルカードサポート発生率を増加」 |
| 4 | 5 / 5 | カードごとに異なる |
| 5 | 10 / 10 | カードごとに異なる |
| 6 | 21 / 25 | 全カード共通:「このカードのサポートイベントによる上昇量を増加」 |

主な種類(SSR の最大値):

| 種類 | 例 |
|---|---|
| 初期ステータス | 初期パラメータ+65、パラメータボーナス+8.5%、最大体力+9、初期育成pt+40、特別レッスン発生率+28% |
| レッスン終了時 | パラメータ+6、特別レッスン終了時パラメータ+17、特別レッスン終了時体力回復+7 |
| スキルカード | アクティブ/メンタル獲得時パラメータ+3、強化時+9、削除時+11 |
| 行動選択時 | 相談+18、おでかけ終了時+15、支給+17、休む+22、授業終了時+7 |
| 試験終了時 | パラメータ+22(プロデュース中2回) |

- サポートアビリティと育成アイテムの発動タイミングが同じ場合、サポートアビリティが先。
- 特別レッスン発生率は**パラメータ別**(例: 歌唱の特別レッスン発生率)。判定の順は [produce.md](produce.md) 10.3 [決定。2026-10-31]
- **MVP で作るのは枠 1(開始時の効果: 初期パラメータ・パラメータボーナス・最大体力)だけ** [決定。2026-10-31]。プロデュース開始時に 1 回、編成の順に適用する。枠 3・6 はスキルカードサポート・サポートイベント(MVP では作らない)にかかる。ほかのトリガー(レッスン終了時・スキルカード・行動選択時・試験終了時)は次点
- **枠 1 の持ち方** [決定。2026-10-31]: マスタ `SupportAbility`(6章)の行で持つ。1 枚に複数の行(効果)を持てる。各行は効果の種類(`InitialParam` / `ParamBonus` / `MaxHp`)、対象のパラメータ(`ParamKind`。最大体力では使わない。3 つ全部に効くものは 3 行にする)、Lv1 の値、最大レベル(完凸時の上限レベル)の値を持つ。Lv1 から有効
  - レベル L の値 = `Lv1の値 + floor((最大の値 − Lv1の値) × (L − 1) / (最大レベル − 1))`(整数の線形補間)。最大レベルは、同じレアの `SupportLevelCap` の `LimitBreak` = 4 の `MaxLevel`。L は 1 以上・最大レベル以下(レベル上げの検証で保証される)
  - 開始時のパラメータ = 育成アイドルの初期値(`Initial*`) + 枠 1 の `InitialParam`(パラメータごとの合計)。足すときは [produce.md](produce.md) 4.3 の「パラメータの加算の関数」を通す(上限で止まる)
  - 最大体力の加算は開始時の最大体力に足す。プロデュースの開始時の体力は最大体力と同じ([produce.md](produce.md) 10.5)
- 単位: パラメータボーナスは千分率(1.2)、発生率は万分率、パラメータ・体力は整数

### 2.4 サポートイベント [確認。MVP では作らない]

- SSR は3つ、SR・R は2つ。1つ目は初期、2つ目は Lv20、3つ目は Lv40 で解放。
- SR 以上の1つ目は、専用のスキルカードか育成アイテムの獲得。週の行動を選んだ後、行動が始まる**前**に発生する。
- 2つ目以降は行動の**後**に発生する。R の 1 つ目も行動の後に発生する [決定。2026-10-31]

| 効果 | R | SR | SSR |
|---|---|---|---|
| パラメータ上昇 | 10 | 15 | 20 |
| 体力回復 | - | - | 7 |
| 育成pt | 10 | 25 | - |

- 発生の判定は**イベントごと**(3章の確率。判定の順は [produce.md](produce.md) 10.3)[決定。2026-10-31]

### 2.5 スキルカードサポート [MVP では作らない]

- レッスン・試験中に確率で発生し、手札のカード1枚を強化する。参考作品はそのターンだけ、最大3段階。[確認]
- カードごとに発動するレッスン・ターンの種類が決まっていて、確率は大・中・小の3段階。[確認]。「レッスン・ターンの種類」は、レッスンの種類(通常・特別・仕上げ・試験)と、試験なら審査ターンのパラメータ。カードごとにマスタで持つ
- Uta では「**そのレッスンの間ずっとレッスン中強化(+)にする**」に単純化する [決定。2026-10-31]。2 段階目以上の性能の定義がなく、既存のレッスン中強化([lesson-card.md](lesson-card.md) 12章)だけで表せるため。強化済みのカードには発生しない。参考作品の段階(最大 3)は持たない

### 2.6 レンタル枠 [決定。MVP では作らない]

参考作品は他プレイヤーのカードを借りるが、Uta ではサーバーのマスタから貸し出す。

- レンタル候補はマスタで定義する(カード、レベル、上限解放回数)。
- 編成画面で、サーバーが候補一覧を返し、プレイヤーが1枚選ぶ。
- 性能はサーバー側で確定させる。クライアントから送られた性能は信用しない。
- 他プレイヤーのカードは借りない(ソーシャル機能は作らない)。
- RPC は [api-design.md](../architecture/api-design.md) 1章の `GetRentalCandidatesAsync`、マスタの区分は [masterdata-pipeline.md](../architecture/masterdata-pipeline.md) 4章の `[ServerOnly]`
- MVP の後に作る理由: `[ServerOnly]` マスタとサーバーが決める候補の技術検証の題材になる。MVP の 1 周には要らない

## 6. マスタの表 [決定。2026-10-31。名前は仮]

列の型は [masterdata-pipeline.md](../architecture/masterdata-pipeline.md) 3章の規約(`int` / `long` / `string` / `bool` / enum)。新しく作る enum(`Recommend`・`Type`・`Kind`)は 0 を `None` にする。`Rarity`・`Plan`・`ParamKind` は既にある `Uta.Domain` の enum をそのまま使い、0 が有効な値(`N`・`Free`・`Singing`)なので「0 は `None`」の規則の外([lesson-enums.md](../architecture/lesson-enums.md) 1章)。そのため空欄を検証で弾けない列は `IValidatable` で別に見る: `Idol.Plan` は `Free` 以外、`Idol.Rarity`・`SupportCard.Rarity` は R 以上。`SupportAbility` の `MaxHp` の行の `Param` は `Singing`(0)を入れ、読まない。MVP で使うものだけを書く。具体の行は masterdata の最初の実装計画で作る([game-spec.md](../overview/game-spec.md) MVP の最小のコンテンツ)。

| テーブル | 主キー | 列 | 区分 |
|---|---|---|---|
| `Idol` | `IdolId` | `Name`、`Rarity`(enum)、`Plan`(enum)、`Recommend`(enum: `None` / `GoodCondition` / `Focus` / `Impression` / `Motivation`)、`MaxHp`、`InitialSinging` / `InitialRhythm` / `InitialExpression`、`BonusSingingPerThousand` / `BonusRhythmPerThousand` / `BonusExpressionPerThousand`、`ExamPatternId`、`FirstParam` / `SecondParam` / `ThirdParam`(`ParamKind`。審査比率の 1〜3 番)、`UniqueCardId` | Common |
| `IdolRecommendDeck` | `Recommend` + `Order` | `CardId`(1.3 の表。1 つのおすすめ効果に 3 行。同じカードは 2 行) | Common |
| `SupportCard` | `SupportCardId` | `Name`、`Rarity`、`Type`(enum: `None` / `Singing` / `Rhythm` / `Expression` / `Assist`)、`Plan` | Common |
| `SupportAbility` | `SupportCardId` + `Order` | `Kind`(enum: `None` / `InitialParam` / `ParamBonus` / `MaxHp`)、`Param`(`ParamKind`。`MaxHp` では使わない)、`ValueAtLv1`、`ValueAtMax`(`ParamBonus` は千分率) | Common |
| `SupportLevelCost` | `Rarity` + `Level` | `SupportPoints`、`Gold`(Level → Level+1 に要る量) | Common |
| `SupportLevelCap` | `Rarity` + `LimitBreak` | `MaxLevel` | Common |
| `InitialSupportCard` | `Order` | `SupportCardId` | ServerOnly |
| `InitialSetting` | `Id`(1 行だけ) | `GachaCurrency`(初期付与。2,500)、`Gold`(10,000 [仮])、`SupportPoints`(10,000 [仮]) | ServerOnly |
| `CommonDeckCard` | `Order` | `CardId`(初期デッキの共通の 5 枚。1.3 の F01×2・F02×1・F03×2 の 5 行) | Common |

- 完凸後の重複の変換量は、ガチャの `DuplicateConversion`([gacha.md](gacha.md) 3.1)に置く
- 初期デッキのカード ID は、14章の記号に対応するマスタのカード ID を `CommonDeckCard`・`IdolRecommendDeck`・`UniqueCardId` に書く
