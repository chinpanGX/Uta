# ADR 0014: 設計は厚く書き、実装は Sonnet のサブエージェントに任せる

> **superseded**（2026-10-31）: [ADR 0017](0017-spec-design-plan-stages.md) で置き換えた。決定は ADR 0017 に引き継ぎ、仕様・実装設計書・実装計画の 3 段に分けた。

## 状況

Uta は個人開発で、作業の多くを Claude に任せている。強いモデル（Opus・Fable）で実装まで回すと、利用枠を早く使い切る。egm の設計書レビューを丸ごと回したときも、途中でトークンが尽きて最後まで終わらなかった。

一方、実装を安いモデル（Sonnet）に任せると、設計書に書かれていない判断をそのモデルが勝手に埋めてしまい、ADR や仕様から外れやすい。

これまでの流れ（CLAUDE.md「実装前のルール」）は「仕様ページを書く → 実装する」で、仕様と実装のあいだに、**どのファイルに何を書くか**を決める文書がなかった。

## 決定

[obra/superpowers](https://github.com/obra/superpowers) の進め方（計画を細かく書き、タスクごとに新しいサブエージェントに実装させ、そのたびにレビューする）を Uta に取り入れる。

1. **仕様**（`uta_docs/wiki/systems/`・`architecture/`）: 何を作るか。これまでどおり
2. **実装計画**（`uta_docs/plans/`）: どのファイルに何を書くか。触るファイル、型とシグネチャ、手順、テストの中身まで書く。書式は [plans/README.md](../../plans/README.md)
3. **設計書のレビュー**（`requesting-design-review`）: 仕様と実装計画をレビューする。実装計画では、**実装を担当するモデル（Sonnet）自身が「質問せずに書ける」と判断すること**を通過の条件にする
4. **実装**: 実装計画のタスクごとに Sonnet のサブエージェントを出す
5. **コードレビュー**（`requesting-code-review`）: タスクごと、またはマージ前に
6. **反映**: 実装と仕様のズレを wiki に戻し、`log.md` に追記する

モデルの使い分け:

| 作業 | モデル |
|---|---|
| 仕様・実装計画を書く | メインのセッション（Opus または Fable） |
| 設計書のレビュー | 観点ごとの Goldfish（`.claude/agents/uta-goldfish-*.md` の定義で固定。整合性は Opus、実装可能性は Sonnet、設計の批評は Fable） |
| 実装 | Sonnet |

実装担当（Sonnet）は、**計画に書かれていない設計判断に出会ったら、自分で決めずに止まって報告する**。計画を直してから続ける。

実装計画の基準には、egm（[google/elephant-goldfish-model](https://github.com/google/elephant-goldfish-model)、Apache-2.0）の Implementation Readiness Standard の考え方を使う。中心は **Zero-Decision Rule**（実装する人に設計判断を一つも残さない）と、各フェーズが終わったときにビルド・テストできる状態であること。

## 理由

- 判断が要る作業（仕様・計画・批評）にだけ強いモデルを使い、量の多い作業（実装）を安いモデルに回すと、利用枠に対して進む量が増える。
- 判断を計画に寄せておくと、実装担当が勝手に決める余地がなくなる。ADR・仕様から外れたかどうかを、計画との差で確かめられる。
- 実装可能性を Sonnet 自身に判定させると、「強いモデルには分かるが Sonnet には書けない」計画を通さずに済む。
- Uta は既に superpowers からコードレビューのスキル（`requesting-code-review`）を取り込んでおり、同じ進め方にそろう。

## 検討した代替案

- 実装もメインのセッション（Opus・Fable）で行う: 一番確実だが、利用枠を早く使い切る。これまでのやり方
- 仕様ページに実装計画まで書く: 仕様ページが長くなり、「何を作るか」と「どう作るか」が混ざる。仕様は長く残るが、計画は実装が終われば役目を終える
- 実装計画を `uta_docs/raw/` に置く: raw は一度置いたら書き換えない決まりなので、レビューで何度も直す計画には合わない
- 実装計画を `scratch/`（Git の管理外）に置く: 実装担当のサブエージェントに渡す正本が履歴に残らず、計画と実装のズレを後で確かめられない

## 影響・リスク

- 実装の前に計画を書いてレビューする手間が増える。小さな変更まで計画を求めると遅くなるので、計画が要る変更を決める（[plans/README.md](../../plans/README.md) の「計画を書くとき」）。
- 計画が細かいほど、仕様と計画の二重管理になりやすい。計画には仕様を書き写さず、仕様ページへリンクする。
- 実装を任せるスキル（superpowers の subagent-driven-development に当たるもの）と、計画を書くスキル（writing-plans に当たるもの）は**まだない**。それまでは、メインのセッションが plans/README.md の書式で計画を書き、手で Sonnet のサブエージェントに渡す。
- Fable・Opus を使うレビューは利用枠を多く使う。重すぎる場合は、まず整合性の観点を Sonnet に下げる。
- コードレビューのモデルはまだ決めていない。

## 見直す条件

- Sonnet が計画どおりに実装できず、止まって報告する回数が多い（計画の粒度が合っていない、または Sonnet に任せる範囲が広すぎる）
- 計画を書いてレビューする手間が、実装の手間を上回るようになった
- 使えるモデル・プランが変わった
