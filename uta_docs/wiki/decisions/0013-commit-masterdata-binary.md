# ADR 0013: マスタのバイナリもコミットする

## 状況

[ADR 0007](0007-masterdata-with-addons.md) では「生成したソースはコミットし、バイナリはコミットせず、ビルドのときに作る」と決めた。しかし CI は、最初は手動で流す（[repository-layout.md](../architecture/repository-layout.md) 11.2）。バイナリをコミットしないと、clone した直後や CSV を変えた後に、生成の手順（.NET SDK とアドオンのツール）を流さないと Unity で動かせない。生成したソースをコミットする理由（ツールがなくても Unity でプロジェクトを開ける）とも揃っていない。

## 決定

- **マスタのバイナリ（`masterdata.bytes`）とマニフェスト（`manifest.json`）を、クライアント用・サーバー用ともにコミットする**。ADR 0007 のうち「バイナリはコミットせず、ビルドのときに作る」の部分を、この ADR が置き換える（ADR 0007 のそれ以外は有効）
- **生成は CSV または定義を変えたときだけ行う**。クライアント用のバイナリは、暗号化のソルトと IV を毎回乱数で作るため、中身が同じでも生成するたびにバイトが変わるため
- CSV を変えたら、同じコミットでバイナリも作り直す。レビューは CSV の差分で行い、バイナリの差分は見ない

## 理由

- clone した直後から、ツールなしで Unity のエディター・実機で動かせる。生成したソースをコミットする方針と揃う
- 手動の CI の間に「生成し忘れて動かない」が起きにくい
- 個人開発なので、バイナリの衝突はほとんど起きない。サイズも小さい（推測。マスタの量が増えたら見直す）

## 検討した代替案

- コミットしない（ADR 0007 のまま）: 差分がきれいで、古いバイナリが残る心配もないが、動かす前に必ず生成が要る
- Git LFS で管理する: 大きなバイナリには向くが、今のサイズでは手間に見合わない

## 影響・リスク

- **CSV を変えてバイナリを作り直し忘れると、古いバイナリがコミットされる**。今の `master-gen --check` は生成ソースしか見ない。アドオンに「`--check` でバイナリの古さも検出する」を足すまでは、運用で防ぐ（[masterdata-pipeline.md](../architecture/master/masterdata-pipeline.md) 8章）
- 中身が同じでも、生成すると差分が出る。アドオンに「データのハッシュが同じならファイルを書き換えない」を足すまでは、変えたときだけ生成する運用で防ぐ（同 8章）
- マスタのバイナリを無視する `.gitignore` は足さない

## 見直す条件

- バイナリが大きくなり、リポジトリの肥大が問題になったとき（Git LFS か、コミットしない方式に戻す）
- CI で生成とビルドを自動化し、clone 直後に生成が要っても困らなくなったとき
