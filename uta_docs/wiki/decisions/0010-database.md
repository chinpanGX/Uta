# ADR 0010: DB は PostgreSQL + Npgsql + Dapper にし、プロデュースのセッションは状態を1列にまとめて保存する

## 状況

プレイヤーデータ（所持品、通貨、ガチャ履歴、プロデュースのセッションなど）を保存する DB を決める必要がある。サーバー基盤（[ADR 0004](0004-server-foundation.md)、[architecture/server-foundation.md](../architecture/server/server-foundation.md)）は PostgreSQL + Npgsql + Dapper を推奨している。プロデュースのセッションは、レッスン中の山札・手札・ステータスなど構造が大きく、仕様の変更で形も変わる。

## 決定

- **DB は PostgreSQL、アクセスは Npgsql + Dapper**（基盤の推奨どおり）
- **プロデュースのセッションは、検索に使う列と、状態を丸ごと入れた1列に分ける**
  - 検索に使う列: ユーザー、状態、週、ターン、バージョン
  - 状態: サーバーで MessagePack にして `bytea` に入れる
  - バージョン列で楽観ロックをかける
- マイグレーションのツールは別途決める

詳細は [architecture/api-design.md](../architecture/api-design.md) 3章。

## 理由

- VolTech-MagicOnion（基盤）と揃い、冪等性・トランザクションの仕組みをそのまま使える
- セッションは1ターンの読み書きが1行で済み、状態の構造を変えても DB のスキーマを変えずに済む
- MessagePack はすでに通信で使っており、`jsonb` より容量と変換のコストが小さい

## 検討した代替案

- EF Core: マッピングは楽だが、基盤と揃わず、生成される SQL を把握しにくい
- セッションを `jsonb` にする: SQL で中身を見られデバッグしやすいが、容量と変換のコストが増える
- セッションを正規化する（山札・手札などをテーブルに分ける）: 中身を検索できるが、1ターンごとの書き込みが多く、仕様変更のたびにスキーマが変わる

## 影響・リスク

- SQL は手書きになる
- セッションの中身を SQL で見たり検索したりしにくい。調査用に、状態を読める形で出す手段（管理用のツールなど）が要る可能性がある
- 状態の形式を変えるときは、保存済みのセッションを移行する仕組み（形式のバージョンを持つなど）が要る
- サーバー専用の型を MessagePack にするため、`Uta.Domain` の型をそのまま保存するか、サーバー側で包むかを実装時に決める（`Uta.Domain` は MessagePack に依存させない。[ADR 0008](0008-shared-domain-and-onion.md)）

## 見直す条件

- セッションの中身を横断して集計・調査する必要が頻繁に出たとき（`jsonb` か正規化を検討）
- 基盤が DB の推奨を変えたとき
