# ADR 0024: 動作検証を実装計画で決め、品質の担保を動作検証に寄せる。設計の批評のレビューをやめる

[ADR 0017](0017-spec-design-plan-stages.md) を置き換える（3 段の設計書は、下の「ADR 0017 から引き継ぐもの」としてそのまま残す）。

## 状況

ADR 0017 の流れは、品質の担保をレビューに寄せていた。設計書は 3 つの観点（整合性・実装可能性・設計の批評）の Goldfish で見る。コードは、レイヤーごとのレビュー担当（Opus・xhigh）で見る。2026-11-02〜11-16 の Uta の transcript（`~/.claude/projects/` のメインとサブエージェント）を集計すると、入力トークンの内訳は次のとおりだった。

| 担当 | 入力（読み直しを含む） | 割合 | 備考 |
|---|---|---|---|
| メインのセッション（進行役） | 764M | 61% | 1 セッションのピークの文脈が 45〜58 万トークン。大きいのは実装のセッション |
| `uta-code-reviewer`（Opus・xhigh） | 176M | 14% | |
| `uta-implementer`（Sonnet） | 106M | 8% | タスクごとに計画を読む。計画は大きいもので 14〜23 万字 |
| `uta-goldfish-consistency`（Opus） | 103M | 8% | |
| `uta-goldfish-readiness`（Sonnet） | 61M | 5% | |
| `uta-goldfish-critique`（Fable・xhigh） | 46M | 4% | 出力が 3.4M トークン（ほかの担当の 2〜4 倍）。料金の高い出力に偏る |

また、次のことも起きた。

- 批評の指摘に応えるたびに、計画に「読み替え」の節（「この節が本文と食い違ったら、この節が正」）が足された。client/ の画面の基盤の計画では、この節だけで 4.8 万字ある。実装担当は、タスクごとにこの計画を丸ごと読む
- レビューは文書を見るので、「Editor で動くか」を確かめていなかった。ユーザーは、Editor で遊べるところまで早く進めたい

ユーザーの判断（2026-11-16）: 敵対的なレビュー（設計の批評）をやめる。代わりに、動作検証を厚くする。動作検証の項目は実装計画の段階で決める。コードレビューは、動作検証が通った後に行う。そのぶん effort を下げてよい。

## 決定

### 設計書のレビュー

- **設計の批評の観点（`uta-goldfish-critique`）をやめる。** 観点は、整合性（Opus）と実装可能性（Sonnet）の 2 つにする
- 段ごとの回し方は、ADR 0017 から観点を 1 つ減らしたものにする

| 段 | レビュー |
|---|---|
| ゲームの仕様（`systems/`・`overview/`） | 整合性だけ。変えたときに 1 回 |
| 実装設計書（`architecture/`） | 整合性・実装可能性。ページ全体のレビューは 2 回まで |
| 実装計画（`uta_docs/plans/`） | 整合性・実装可能性。実装可能性（Sonnet）が「質問せずに書ける」と判定するまで直す |

- 「書く前に弱点を洗う」「範囲（YAGNI）の自己点検」は、計画を書く進行役が自分で行う（[uta-plan](../../../.claude/skills/uta-plan/SKILL.md)）。サブエージェントは出さない

### 動作検証を実装計画で決める

- 実装計画に「動作検証」の章を置く（[plans/README.md](../../plans/README.md) の 5章。旧「テスト」の章を置き換える）。書くことは次のとおり
  - タスクごとの確かめ方を、実行できるコマンドと、期待する結果（通る件数・出力・終了コード）で書く。コマンドは CLAUDE.md「ビルド・テスト・実行」にあるものだけ。「目で見て確かめる」だけの確かめ方は書かない
  - 足すテストケース。正常系と境界ごとに並べる
  - 計画全体の受け入れ（全部のタスクが終わった後に回すもの）
- レイヤーごとに使う動作検証:

| レイヤー | 動作検証 |
|---|---|
| shared | `dotnet test --project shared/Uta.Shared.Domain.Tests` |
| server | `dotnet test --project server/Uta.Server.Tests`（結合テストを含む。Docker が要る） |
| client | EditMode のテストと、**PlayMode のテスト**。画面・遷移・通信を触るタスクは、PlayMode のテストで確かめる |

- **client の PlayMode のテストは、基盤（PlayMode の asmdef・テストの回し方・テスト用のサーバーの用意）を別の計画で作る。** 基盤ができるまでは、client のタスクは EditMode のテストと `unity recompile` で確かめ、PlayMode で確かめるはずのものを「未確認」と実装メモに書く。基盤ができたら、画面・遷移・通信を触るタスクでは PlayMode のテストを必須にする
- 実装可能性の観点（Sonnet）は、動作検証の章も見る。コマンドが実在すること、期待する結果が書かれていること、タスクごとに確かめ方があることを確かめる

### 実装の順番: 動作検証 → コードレビュー

1. タスクごとに、実装担当（Sonnet）が実装し、そのタスクの動作検証を自分で回す。結果を報告に書く
2. 進行役が同じコマンドを回し直してから、コミットする
3. 全部のタスクが終わったら、計画の「受け入れ」を回す
4. **受け入れが通ってから、コードレビューに出す。** コードレビューは、動くことの確認ではなく、規約・層の依存・仕様との一致・AOT の制約など、動作検証で見つからないものを見る。レビュー担当には、動作検証の結果を渡す
5. コードレビュー担当（`uta-code-reviewer`）は、Opus のまま effort を xhigh から medium に下げる

### 計画とセッションの肥大を抑える

- **計画に「読み替え」の節を足さない。** レビューへの対応・方針の変更・コードレビューへの対応は、本文の該当の節を直接書き換える。変えた経緯はコミットメッセージに書く（[ADR 0018](0018-change-log-from-git.md)）
- **実装担当には、計画の全文を読ませない。** 読むのは「この計画で決めたこと」・1章・担当のタスク・そのタスクが挙げた 3章の節・5章のそのタスクの分だけにする。計画のタスクには、参照する 3章の節を書く
- **実装のセッションを区切る。** タスクを 4〜5 個終えたとき、または文脈が 20 万トークンを超えたら、実装メモを更新して、続きを新しいセッションで始める

### ADR 0017 から引き継ぐもの（変えない）

- 設計書を 3 段（ゲームの仕様・実装設計書・実装計画）に分け、段ごとに書くことと書かないことを分ける。依存の向きは「計画 → 実装設計書 → 仕様」。表は ADR 0017 の「決定」の表のとおり
- 詳細は実装設計書で決める。ページ全体のレビューを 2 回回しても細部の指摘が続くなら、ページのレビューは止め、実装計画ごとのレビューで詰める
- 設計は厚く書き、実装は Sonnet のサブエージェントに任せる。計画にない設計判断に出会ったら、実装担当は止まって報告する
- 計画の基準は egm の Zero-Decision Rule
- 仕様・実装設計書・計画を書くのは、メインのセッション（Opus または Fable）
- コードを変えたら、関係する実装設計書を同じ変更で更新する。ゲームの挙動が変わったときだけ、仕様も更新する

## 理由

- 批評は、根拠の要る代案を毎回出すので、計画が膨らみ、出力のトークンが重い。範囲の点検（YAGNI）は、計画を書く進行役の自己点検でも安く見られる
- 文書のレビューで「動く」とは言えない。動くかどうかはテストを回せば決まり、モデルの判断に頼らない。テストは一度書けば、後の変更でも回し直せる
- 動作検証の項目を計画で決めると、実装担当は終わりの条件が分かる。進行役は、差分を読まずにコマンドの結果で確かめられる
- コードレビューの前に動作検証を通すと、レビュー担当は動作を推測で追わずに済む。規約と構造に絞れるので、effort を下げられる
- トークンの 61% は進行役の読み直しで、大きいのは実装のセッション。計画の全文を読ませないこと、セッションを区切ることが一番効く

## 検討した代替案

- 設計書のレビューを全部やめ、自己点検と動作検証だけにする: 実装可能性（Sonnet）の判定は、実装担当が止まる回数を減らす関門として効いている。整合性の見落とし（ADR との食い違い）は、テストでは見つからない
- コードレビューを Sonnet に下げる: ユーザーは effort を下げることを選んだ。モデルは Opus のまま残す
- 計画の大きさに上限（1 本 5 万字）を置く: ユーザーは選ばなかった。読み替えの禁止と、タスクの節だけを読ませることで、実装担当が読む量は減る

## 影響・リスク

- `.claude/agents/uta-goldfish-critique.md` と `.claude/skills/requesting-design-review/lenses/critique.md` を消した。過去のレビューの報告（`uta_docs/reviews/`）にある批評の指摘は、そのまま残す
- 2026-11-16 の時点で `ready`・`in-progress` の計画は、旧い書式（5章「テスト」、読み替えの節）のままで実装してよい。書き直さない。新しく書く計画から、この ADR の書式にする
- client の PlayMode のテストの基盤がない。基盤の計画ができるまでは、画面の動作は「未確認」になり、ユーザーが Editor で確かめる
- 批評をやめたので、過剰な設計・根拠のない前提は、進行役の自己点検（[uta-plan](../../../.claude/skills/uta-plan/SKILL.md) の 3・6）でしか見ない。見落としは、実装の後の動作検証とコードレビューで拾う

## 見直す条件

- 実装担当が、計画にない設計判断で止まることが増えたとき（設計書のレビューを足すか、計画の基準を見直す）
- 実装の後に、設計からのやり直し（層・型・テーブルの作り直し）が続くとき（批評の観点を戻すかを考える）
- PlayMode のテストの基盤ができたとき（client の動作検証の既定を見直す）
