# ADR 0017: ゲームの仕様・実装設計書・実装計画の 3 段に分け、レビューは実装設計書と計画で回す

[ADR 0014](0014-design-heavy-sonnet-implementation.md) を置き換える（ADR 0014 の決定は、下の「ADR 0014 から引き継ぐもの」としてそのまま残す）。

## 状況

ADR 0014 は「仕様（`systems/`・`architecture/`）→ 実装計画 → 設計書のレビュー → Sonnet が実装」と決めたが、仕様の置き場を `systems/` と `architecture/` でひとまとめにしていた。その結果、次のことが起きた（2026-10-31 の設計書レビュー）。

- `systems/` のゲームの仕様のページに、乱数の引き方・セッションの状態・SQL・RPC と DTO などの実装設計が入り、同じことが `architecture/` のページと 2〜3 か所に書かれた。
- そのページ全体に 3 つの観点のレビューを何度も回し、直した記述から新しい食い違いが出て、指摘が減らなかった。3 回目のレビューの Critical のうち 3 件は、前の回の修正で入った食い違いだった。
- 15 体のレビューの報告で進行役のコンテキストが埋まった（[requesting-design-review](../../../.claude/skills/requesting-design-review/SKILL.md) は報告をファイルに書かせる形に直した）。

ユーザーの意図は、egm の考え方で**実装設計書の段階でレビューを回して詳細を決め、コーディングは Sonnet に任せる**ことだった。

## 決定

設計書を 3 段に分け、段ごとに書くことと、レビューの回し方を決める。

| 段 | 置き場 | 書くこと | 書かないこと | レビュー |
|---|---|---|---|---|
| ゲームの仕様 | `wiki/systems/`・`wiki/overview/` | 何が起きるか: ルール・値・局面の遷移・実行要件・MVP の範囲 | SQL、DTO、型名、層の置き場、乱数の引き方、テストの作り方 | 整合性の観点だけ。変えたときに 1 回 |
| 実装設計書 | `wiki/architecture/` | どう作るか: 層と依存、型、RPC・DTO・エラー、テーブル、処理の手順、乱数・状態・再現。根拠として仕様の節にリンクする | ゲームのルールの説明（仕様にリンクする） | 3 つの観点。**詳細はここで決める**。ページ全体のレビューは 2 回まで |
| 実装計画 | `uta_docs/plans/` | どのファイルに何を書くか: シグネチャ、DDL、手順、テストの中身 | 決まりそのもの（実装設計書にリンクする） | 3 つの観点。実装可能性（Sonnet）が「質問せずに書ける」と判定するまで直す |

- **ゲームの仕様は実装設計書の一次情報**。変えるのは、ゲームの仕様（遊ぶ人から見える挙動）が変わるときだけ。実装の都合で変わるもの（SQL・型名・置き場・テスト）は、実装設計書と計画の中だけで直す
- 依存の向きは「計画 → 実装設計書 → 仕様」。仕様は実装設計書の中身に頼らない
- コードを変えたら、関係する**実装設計書**を同じ変更で更新する。ゲームの挙動が変わったときだけ、仕様も更新する
- ページ全体のレビューを 2 回回しても細部の指摘が続くなら、ページのレビューは止め、実装計画ごとのレビューで詰める

ADR 0014 から引き継ぐもの（変えない）:

- 設計は厚く書き、実装は Sonnet のサブエージェントに任せる。計画のタスクごとに出し、計画にない設計判断に出会ったら止まって報告させる
- 計画の基準は egm（[google/elephant-goldfish-model](https://github.com/google/elephant-goldfish-model)、Apache-2.0）の Zero-Decision Rule
- モデルの使い分け: 仕様・実装設計書・計画を書くのはメインのセッション（Opus または Fable）、レビューは観点ごとの Goldfish（整合性は Opus、実装可能性は Sonnet、設計の批評は Fable）、実装は Sonnet
- コードレビューは `requesting-code-review`。実装と設計書のズレは wiki に戻し、`log.md` に追記する

## 理由

- 仕様と実装設計を分けると、同じことを 1 か所でしか書かないので、ページ同士の食い違いが減る。
- 詳細を決める場（実装設計書）を 1 つにすると、レビューを回す場所が絞られ、利用枠に対して進む量が増える。ゲームの仕様は実装の都合で揺れないので、軽い点検で足りる。
- 実装計画を Sonnet 自身に判定させる関門（ADR 0014）は、そのまま効く。

## 検討した代替案

- ADR 0014 のまま、仕様ページに実装設計も書く: 今回の状態。ページが長くなり（produce.md が 700 行を超えた）、レビューが収束しない
- 実装設計をすべて実装計画に書く: 計画は実装が終われば役目を終えるので、長く残すべき設計（状態の持ち方・処理の手順）が残らない
- システムごとにフォルダを分ける（`systems/produce/` に仕様と設計を並べる）: 層をまたぐ決まり（依存・規約）の置き場が分かれ、横断して読みにくい

## 影響・リスク

- 2026-10-31 に、`systems/` の実装設計を `architecture/` に移した: produce.md の 10章と API案 → `architecture/produce-domain.md`、gacha.md の抽選の実装・処理の手順と idol-support.md の強化の手順 → `architecture/gacha-support-server.md`、lesson-card.md の 15章 → `architecture/lesson-phases.md`。中身は変えていない
- `systems/` のマスタの表（列の定義）は、[masterdata-pipeline.md](../architecture/master/masterdata-pipeline.md) 9章の索引が「列の正は各システムのページ」としているので、今は動かさない。仕様と実装設計の境目にあるもので、動かすかは別に決める
  - 追記（2026-10-31。ユーザーの判断）: 同じ日に、マスタのテーブル・列・区分・検証を `architecture/master/` のシステムごとのページ（`*-tables.md`）に移した。マスタの表の正は実装設計書で、`systems/` には「何を持つか」だけを残す。全テーブルの索引は [master/README.md](../architecture/master/README.md)
- 線の引き方で迷うものが出る（乱数の引く順は結果の値を変えるが、仕様ではなく作り方とする、など）。迷ったら `architecture/README.md` の「何の正がどのページか」の表に足して決める
- ページの置き場（目次）は各フォルダの `README.md` に置く（index.md は入口だけにした）

## 見直す条件

- 実装設計書のレビューでも指摘が収束しないとき（設計書の粒度か、レビューの回し方を見直す）
- 実装担当（Sonnet）が計画にない設計判断で止まることが多いとき（計画の基準を見直す）
