## 判定

## 指摘

### Critical

#### C1. 効果の列の対応と enum の名前が、masterdata-pipeline.md 3.1 とコード（lesson-domain-types.md 2.1）で別物
- 場所: 7章冒頭（226行目「op ごとの列と、ステータス・トリガー・コスト・条件の enum は masterdata-pipeline.md 3.1 が正」）、6.1（215行目）、masterdata-pipeline.md 3.1、lesson-domain-types.md 2.1（20行目「効果はマスタと同じ汎用の形で持つ」）、`shared/Uta.Domain/Lesson/LessonEnums.cs`・`EffectExecutor.cs`・`CardDefinitionValidator.cs`
- 出した観点: 整合性 C1・実装可能性 C1
- 食い違い:
  - 型名: pipeline `Op` / `TriggerKind`、コード `EffectOp` / `PersistentTrigger`
  - `StatusKind`: pipeline は `Genki` を含み `CostDown` / `CostUp`（13 個）、コードは `Genki` なし（元気は `LessonState` に持つ）で `CostHalf` / `CostDouble`（12 個）。並びも違う
  - トリガー: pipeline に `EveryNTurns` あり、コードになし（pipeline・lesson-card 15.1 は「enum は最初から全部定義」）
  - `Comparator`: `Ge/Le/Eq` と `GreaterOrEqual/LessOrEqual/Equal`。`ConditionSubject`: `Turn` / `TargetPercent` と `TurnNumber` / `ClearTargetPercent`
  - 列の使い方: pipeline は対象を型付きの `Status` / `Trigger` 列に入れ、コードは `Arg1` に int で入れて引数が 1 つずつずれる（`AddTurns` / `AddStack`、`ParamByRatio` は別 enum `RatioSource`、`ScaleResource` / `SetResource` は別 enum `ResourceKind`、`AddPercent` のターン数は pipeline `Arg1` / コード `Arg2`、`Schedule` は `Value` / `Arg1`、`Persistent` は pipeline `Arg1`=ターン数・`Arg2`=回数 / コード `Arg1`=トリガー・`Arg2`=ターン数・`Arg3`=回数、`CreateCard` は `Value`=枚数・`Arg1`=置き場）
- なぜ問題か: コード（LessonEnums.cs 3行目）は「マスタ・保存の値に使うので enum の数値は変えない」としている。pipeline の順で `StatusKind` を定義して int のまま渡すと別のステータスとして解釈される。フェーズ 2 の `ScaleResource` / `SetResource` をどちらの形で書くかも決まらない
- 直し方（選択肢）: (a) コードを正とし、pipeline 3.1 と 7章の「3.1 が正」を書き換える（既存コードは変わらない） (b) pipeline を正とし、コードの enum と引数を直す（`Status` / `Trigger` を `EffectDef` の型付きプロパティに、`RatioSource` / `ResourceKind` をやめて `StatusKind` に `Genki`。CSV に名前で書ける利点があるが、フェーズ 1 のコード・テストを書き換える） (c) マスタの形と Domain の形は別物と明記し、変換表を Infrastructure の設計に置く（lesson-domain-types.md 20行目を消す）。いずれも実装メモにズレを記録する。**フェーズ 2 の計画の前に決める**

#### C2. 持続効果に付けた条件の意味が、3 つのページとコードで違う
- 場所: 7.5（275行目 `persistent = { trigger, condition?, effects[], duration? }`）、masterdata-pipeline.md 3.1（147行目「`Persistent` の `RefConditionGroupId` は発動のたびに見る条件」）、lesson-domain-types.md 2.1（68行目「発動の条件は子の効果の効果内条件で表す」）、コード（`EffectExecutor.cs` 73〜81行目、`LessonEngine.cs` 115行目。`Persistent` の行の `Conditions` は使用時の効果内条件として判定され、満たさなければ付与されない。`PersistentEffect` は条件を持たない）

- なぜ問題か: pipeline に従って「発動のたびに見る条件」を書くと、コードは「付与するかどうか」として扱い挙動が変わる。初期カードセットに条件付きの持続効果がないので今は表に出ない

### Important

#### I1. 9.6「数値型」が [Uta案] のままで、理由の「サーバー検証」が ADR 0008 と合わない
- 場所: 9.6（372〜375行目「decimal か整数の固定小数点」「`ceil` の境界で 1 ずれるとサーバー検証が成立しない」）、13章（452行目「サーバー検証・不具合再現・リプレイに使う」）
- 出した観点: 整合性 I1・I2・批評 1
- 問題: 数値型は lesson-domain-types.md「決まっていること」19行目で整数の固定小数点に [決定] 済みで、コードに `decimal` は 1 件もない。repository-layout.md 5章 118行目は `decimal` を含まない。それなのに produce.md 10.0・repository-layout.md 118行目・ADR 0007 37行目・masterdata-pipeline.md 81行目が 9.6 を根拠として参照している。また ADR 0008 ではクライアントは結果を送らず予測を表示するだけで、ずれを許容する（repository-layout.md 6章 135行目）。「サーバー検証」はクライアントの結果をサーバーが検証するモデル（ADR 0008 で採らなかったもの）を連想させる
- 直し方: 9.6 を [決定] にし、「整数（パーセントの整数・万分率）と `long` の分子・分母。`decimal` は使わない」とそろえる。理由を「予測の表示と確定値を一致させやすくするため、および同じシード・操作列での再生テスト（produce.md 10.6）を成立させるため」に書き換える。13章の「サーバー検証」も言い換える

#### I2. 9章の式に、8章で定義していない項がある（低下状態の定義もない）

- 直し方: 順は [確認] なので変えず、10章に「L1 の効果はゾーンを参照・操作しない」と書き、`CardDefinitionValidator` で `LessonStart` 配下の `Draw` / `ReplaceHand` / `EnhanceHand` / `CreateCard` を読み込み時エラーにする

#### I14. 「山札 0 枚・捨札も 0 枚」の後に捨札ができたときの再シャッフルの時点が仕様にない
- 場所: 4章、lesson-domain-types.md 5章（[Uta案]「ドローのときに山札 0 枚で捨札があればそこでも再シャッフル」）、`Zones.Draw`
- 出した観点: 批評 5
- 問題: 4章の規則は「山札が 0 枚になった瞬間」にしか発火しない。乱数を引く時点が変わるので再現性に直結するのに、仕様ページでは未決にも決定にも挙がっていない
- 直し方: 4章に「山札が 0 枚のままドローするときに捨札があれば、その時点で再シャッフルする [決定]」を足す（lesson-domain-types.md の案を正式化）

#### I15. 14章の初期カードセットの数値が参考作品の値そのまま
- 場所: 14章（456〜510行目）、19行目（「仮の値」「バランス調整で差し替える」）、`Uta.Domain.Tests` の `Phase1Cards`、ADR 0001
- 出した観点: 批評 6・整合性（ADR の見直しの提案）
- 問題: ADR 0001 は「模倣してよいのは構造のみ」「抽出データをコード・ドキュメントに入れない」。37 枚分のコスト・効果量・強化後の値の組は、構造というより調整済みのコンテンツに近く、「抽出データ」に当たるかは判断が要る。期待値は 9章の式から出す（15.7）ので、参考作品の値は検証のオラクルにもならない。「差し替える前提」が未決事項にない（produce.md も同じ扱い）
- 直し方（**ユーザーの判断**。抽出データに含めると判断するなら Critical に格上げ）: 代案は「レアリティ × 種別ごとの簡単な規則（例: 消費 1 あたりパラメータ +N、強化で +α）」で Uta 独自の値を機械的に作り、構造（コストの種類・効果の組み合わせ・条件）だけ参考にする。あわせて ADR の見直しの提案（下）を参照

## ADR の見直しの提案

- **ADR 0001（IP 方針）**: 既存作品の「抽出データ」をドキュメントに入れることを禁じているが、数値（カードごとの効果量や構成）がこれに当たるかは書かれていない。lesson-card.md 19行目・14章、produce.md は参考作品の値を仮の値として並べている。数値を仮に使ってよいか、公開前に差し替えが必須かを ADR 0001 に明記し、glossary の「置き換え対象の仮称」と同じように数値の扱いも 1 か所にまとめる提案（整合性。批評の I15 と同じ論点）。ADR 0001 は accepted なので、変えるなら新しい ADR で置き換える
- 批評の I8 は ADR 0008 の「Unity 側のテストは必須にしない」の範囲内で、1 回の確認を手順に足す提案（ADR の変更ではない）
