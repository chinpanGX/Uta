## 判定

| 観点 | 判定 |
|---|---|
| 整合性 | 直せば |
| 実装可能性 | **いいえ**（未決事項と Important を決めてから実装計画に進む） |
| 設計の批評 | 直せば |

**まとめ: 直せば（ただし決めることが多い）。** 排出率・価格は内部でもほかのページとも合っており、サーバー権威・1 トランザクション・冪等性・無償通貨 1 種の骨格は正しい。一方、マスタ表・カード単位の確率・乱数・重複の保持・交換pt の変換が決まっておらず、実装計画を書くと設計判断が連続する。交換メダル・割引単発・常設/ピックアップの種類分けは MVP に要らない複雑さ（批評）。

## 良い点

- 排出率の表の合計がそろう（40 + 60 = 100、5 + 17 + 78 = 100）。ピックアップは内数に収まり、すべて万分率の整数で表せる（masterdata-pipeline.md 3章 `RatePerTenThousand`）。7章の 10 枠目（SSR 5% / SR 95%）も 3章の合計と合う
- 「課金は実装しない。ガチャ通貨は無償の 1 種類だけ」を [決定] にし、限定ガチャを後回しにした範囲の切り方が明確
- 抽選・所持品の更新はサーバー、1 トランザクション、再送の冪等性は基盤（`x-request-id`）に任せる、が噛み合っている
- 「マスタの排出率から表示と抽選の両方を作り、二重管理にしない」（6章）は、表示と実際の確率のずれを構造で防ぐ
- 8章の「バッチにせず `SyncAsync` で変換」は、api-design.md 1章・screen-design.md 4章・glossary「同期」・game-spec.md に同じ内容で反映されている。Cloud Run で常駐ジョブを持たずに済む
- [確認] / [決定] / [Uta案] の凡例がほぼすべての節にある。参考作品の名称・URL はない

## 指摘

### Critical

なし（実装可能性は「I5 重複の処理は実装方法が複数あって結果が変わるので実質最優先」と添えている）

### Important

#### I1. 交換pt の変換方法が 6章と 8章で食い違う
- 場所: 6章「論点」表の「天井と期間」（100行目「バッチ処理が必要」）と 8章（119行目「バッチ処理にせず `SyncAsync`」）
- 出した観点: 整合性 I-1・実装可能性 5・批評 7
- 問題: 同じページで古い論点と新しい決定が両方残っている。バッチなら起動しないユーザーの分も変換されるが、`SyncAsync` では残る。api-design.md・screen-design.md・glossary は 8章の側
- 直し方: 6章の行を「期間終了後の扱いは 8章」に差し替える（I3 で交換メダルを外すなら行ごと消える）

#### I2. 天井（交換pt）の細部が決まっておらず、常設ガチャの「リセット」と `SyncAsync` の「変換」が合わない
- 場所: 1章（36・40行目）、4章（67・68行目）、api-design.md 1章 `SyncAsync`・3章 `gacha_exchange_points`（主キー `player_id + gacha_id`）
- 出した観点: 整合性 I-2・実装可能性 5・批評 5
- 問題:
  - 「ラインナップ更新」がマスタ上の何か（同じ `gacha_id` で中身が替わるのか、`gacha_id` が替わるのか）が書かれていない。前者ならリセットする処理も版の列もない。後者なら旧 ID は `SyncAsync` で交換メダルに変換され、「リセット（失われる）」と結果が違う
  - 常設ガチャにはピックアップがないのに 200pt の交換があり、何と交換するかがない
  - 交換で消費するのは 200pt か全部か、10 連は 10pt か、交換対象が複数（アイドルとサポート）のときどれを選べるか、既に持っているカードを交換したときの扱い
  - 交換pt → 交換メダルの**変換比率がどのページにもなく、未決事項にもない**（`SyncAsync` の実装に必要）
  - `gacha_exchange_points` の「変換済みか」の列、`SyncAsync` が変換結果を DTO で返すか
- 直し方（選択肢）: (a) 同じ ID のまま、リセット用に版の列を足す (b) 更新のたびに新しい ID にし、余った pt は変換する（4章の「リセット」を「変換」に直す） (c) 新しい ID にし、余った pt は失う（`SyncAsync` で常設を除外する条件を書く）。批評の代案: 常設とピックアップの「種類」をやめ、「ガチャはマスタの 1 行（期間・排出テーブル・交換対象の一覧）。呼び分けは運用上のもの」と書けば、リセットは `gacha_id` が変わることで表せ、「ラインナップ更新」という語が要らなくなる

#### I3. 交換メダルが「貯まるだけで使えない通貨」なのに、必須要件と変換処理を引っ張り、GAC-04 に API も画面もない
- 場所: 4章（67行目）、5章（81行目）、6章 GAC-04（93行目）、8章（118・119行目）、api-design.md 1章 `IGachaService`、screen-design.md 2章
- 出した観点: 整合性 I-3・実装可能性 6・批評 1
- 問題: ショップは後回し（8章）なので MVP ではメダルの使い道がない。それでも交換pt → メダルの変換（`SyncAsync`・「変換済みか」列・`players.交換メダル` 列）と、かけら → メダルの変換（GAC-04 必須）が残る。かけら → メダルはプレイヤー操作なのに RPC（`IGachaService` は `GetGachas` / `Draw` / `GetHistory` / `Exchange` だけ）も画面もない。「余った」の定義・変換の単位もない
- 直し方（選択肢）: (a) MVP では交換メダルを作らない。GAC-04 を「重複時のかけら変換」だけにし、メダル変換は後回し。交換pt は期間後もそのまま残す（`SyncAsync` の変換・「変換済みか」列・メダル列・119行目の例外説明が消える） (b) 残すなら RPC を api-design.md 1章に、画面を screen-design.md に足し、用途がないまま持つ理由を書く

#### I4. 「1 日 1 回・ガチャ通貨 60 の割引単発」の扱いがページごとに違う
- 場所: 2章 46行目（[Uta案]）、6章 GAC 表（記載なし）、screen-wireframes.md 9章（`[ 1日1回 60 ]` ボタン）、api-design.md 1章 `DrawAsync`（単発・10 連だけ）・`SyncAsync`（日付更新の処理は「いまは無し」）・3章（「最後に引いた日」の列がない）、repository-layout.md 10.2（日付の更新は 12:00 JST）
- 出した観点: 整合性 I-4・実装可能性 7・批評 2
- 問題: 提案のままで未決事項にも GAC 要件にもないのに、ワイヤーには載っている。本文自身が「参考作品では有償通貨限定の枠」と書いており、有償通貨のない Uta では「安い単発」でしかないのに、日付更新をまたぐ状態を要求する
- 直し方（選択肢）: (a) 削る（ワイヤーのボタンも消す。値下げしたいならマスタで単発の値を下げれば同じ） (b) 採用し、GAC 表に ID を足し、日の区切り（12:00 JST）を明記し、`DrawAsync` に種類を、api-design.md 3章に列を足す

#### I5. 重複したときの処理と、かけらを持つ単位が決まっていない
- 場所: 5章（かけらをカードのレアで換算: SSR 50 / SR 25 / R 5）、idol-support.md 1.1・1.6・1.8・1.9、glossary「かけら」、api-design.md 3章（`player_idols` は `player_id + idol_id`、「かけらは育成アイドルごとに持つ（推測）」）
- 出した観点: 整合性 I-5・実装可能性 6
- 問題:
  - 同じアイドルに R と SSR のカードがある（1.8）なら、アイドルごとのかけらにどのレアの換算を使うか決まらない。1.8 と 1.9（別楽曲のバリエーションは対象外）は、同じアイドルに複数のカードがあるかで食い違って読める。api-design.md の「推測」も確認されていない
  - `player_idols` が「所持している行」か「かけらも含む行」か。未所持のアイドルが出たとき「所持にする」のか「かけらが貯まる」のか（1.8「未所持はかけら 100 で解放」）。同じ 10 連で同じアイドルが 2 回出たときの順序
  - サポートカード: 完凸（5 枚）までの上限解放は自動か手動（`LimitBreakAsync`）か。手動なら所持枚数の列が `player_support_cards` にない。完凸後の「サポート強化pt」は `players` に列がなく、変換量は idol-support.md 3章の未決・7章の案どまり
  - 「ピックアップ入手のたびにおまけでかけら 50 個」（5章 82行目）は [確認] のまま採否がない
- 直し方（選択肢）: かけらは (a) カード（`idol_id` = カード ID）ごとに持つ (b) アイドル本人ごとに持ち、換算はレアによらない値にする。どちらかを idol-support.md に書き、gacha.md 5章・glossary・api-design.md 3章を合わせる。サポートの上限解放の自動/手動と保存列、おまけかけらの採否を決める

#### I6. 排出テーブルのマスタ定義と、カード 1 枚ごとの確率への落とし方がない
- 場所: 3章（48〜62行目）、6章 GAC-02・「確率の表示と実際の一致」（99行目）、masterdata-pipeline.md 3・4章
- 出した観点: 実装可能性 1・2、批評 3
- 問題:
  - テーブル名・主キー・列がない（ガチャ本体、期間、価格、ラインナップ、ピックアップ、レア別の率）。列の型は 5 種で配列・nullable が使えないので、子テーブル + `Order` の設計が要る。常設の「期間なし」の表し方、合計 10000 の `IValidatable`、区分（Common か `[ServerOnly]` か）もない
  - 非ピックアップの SSR 1.25% を何枚でどう割るか（等分か重みか、万分率の端数）、「ピックアップ 0.75%」が 1 枚あたりか合計か、プールが空のとき、ピックアップが複数のときの配分
- 直し方（選択肢）: (a) マスタはカードごとの整数の重みだけを持ち、表示のレア別 % は重みの合計から計算する（端数が消え「二重管理しない」と合う。表示が 2.0% ちょうどにならないのを受け入れる） (b) マスタはレア別率とピックアップ率を万分率で持ち、残りをカード数で等分して端数は先頭に寄せる。いずれもピックアップ率が 1 枚あたりか合計かを明記する

#### I7. 10 連の確定枠の確率の掛け方が未定で、「マスタから表示と抽選の両方を作る」と両立しない
- 場所: 7章（106行目「10 枠目だけ R の確率を SR に振り替える」）、6章 99行目
- 出した観点: 実装可能性 3・批評 4
- 問題: 「振り替える」はサーバー実行時の書き換えに読め、10 枠目の確率がマスタにない（表示は 5/17/78、10 枠目は 5/95）。振り替え後に育成アイドル 40 / サポート 60 の内訳とピックアップ SR 4.0% を保つかが書かれていない
- 直し方（選択肢）: (a) 通常テーブルから R の重みだけを SR に足す (b) SR 以上だけの別テーブルを引き直す。批評の代案: 確定枠も別の排出テーブルとしてマスタに持ち、ガチャが「通常枠のテーブル ID」と「確定枠のテーブル ID」を指す。参考作品の「10 連のどこかに SR 以上 1 枚」ではなく「10 枠目を常に SR 以上」に単純化したと明記する

#### I8. 抽選の乱数源と、履歴の粒度・形式が書かれていない
- 場所: 6章（98行目「1 回ごとに保存」）、api-design.md 3章 `gacha_histories`、repository-layout.md 3章・10.3（シードはサーバーが暗号用乱数で生成。ただしプロデュース向けの記述）
- 出した観点: 実装可能性 4・10、批評 8
- 問題: 暗号用乱数を直接引くのか、要求ごとにシードを作って `xoshiro256**` で引き履歴に残すのか。1 回の抽選で何回・どの順に引くか（レア → 種別 → カードか一括か）、万分率への落とし方（`% 10000` の偏りを許すか棄却法か）、`RandomStreamKind` にガチャ用を足すか、再現が要るか。履歴の 1 行が `DrawAsync` 1 回かカード 1 枚か、確率テーブルの記録形式（列 / MessagePack / JSON）
- 直し方（選択肢）: (a) 暗号用乱数を直接（単純。再現は履歴の結果だけで足りる） (b) シード + `xoshiro256**`（再抽選を再現できるがシード列が増える）。履歴はカード 1 枚 = 1 行で `request_id` で束ねるのが自然（批評の意見）

#### I9. `IGachaService` の DTO とエラーが決まっていない
- 場所: api-design.md 1・2章
- 出した観点: 実装可能性 8
- 問題: RPC 名しかない。`DrawGachaRequest`（`gachaId`、回数を int か enum か、割引、期待価格の照合）、`DrawGachaResponse`（各行のカード ID・種別・レア・新規/重複・かけら量・交換pt・残り通貨）、`GetGachasAsync` で排出率を返すのか（クライアントがマスタを持つなら不要）、`GetHistoryAsync` のページングと保持件数、`ExchangeAsync` の引数。エラーは `GACHA_NOT_ENOUGH_CURRENCY`・`GACHA_OUT_OF_PERIOD` だけで、交換pt 不足・対象外のガチャ・不正な回数などがない
- 直し方: api-design.md 側か実装計画で決めると明記し、エラーの一覧を足す

#### I10. 同時実行の方針がない
- 場所: 完了条件（22行目「1 トランザクションで整合」）、api-design.md 3章
- 出した観点: 実装可能性 9
- 問題: 通貨の減算を `UPDATE ... WHERE gacha_currency >= @cost` にするか `SELECT ... FOR UPDATE` にするか。別の `x-request-id` で同じプレイヤーから同時に 2 件来た場合（冪等性とは別問題）
- 直し方: 同時実行の方針を 1 行決める

#### I11. 天井の完了条件が、今の数値と通貨の入手量では確かめられない。初期付与の量も未決
- 場所: 完了条件（21行目「天井が動く」）、4章（200pt）、2章（単発 250）、produce.md 6.1（報酬 C 100〜S 500）、8章（初期付与）
- 出した観点: 実装可能性 11・批評 6
- 問題: 天井 200 回 = 通貨 50,000 = プロデュース 100〜500 回分。初期付与の量は未決（`players` 作成処理に書く値が要る）。3〜5章の数値は [確認] だけで、Uta として採ったのかが読めない
- 直し方: 3〜5章の数値を「マスタの初期値。Uta で検証できる量に変えてよい」と [決定] で明記する。天井を確かめる手段の選択肢: (a) 初期付与を天井に届く量にする (b) 開発用の通貨付与の手段を api-design.md に足す (c) 天井の pt をマスタで小さくして試す。初期付与は仮の値でよいので置く

#### I12. 新しい用語が glossary にない
- 場所: 1・2・5・7章
- 出した観点: 整合性 I-6
- 問題: 常設ガチャ、ピックアップ（ガチャ）、限定ガチャ、10 連、確定枠、上限解放、完凸、サポート強化pt が glossary にない（後 3 つは idol-support.md でも使う）。glossary の「交換pt」は「200pt でピックアップと交換」で、常設ガチャの交換を含まない
- 直し方: glossary の「育成アイドル・ガチャ」の表に足し、「交換pt」の定義を直す

## 未決事項に加える候補

- 交換pt → 交換メダルの変換比率（I2）
- 常設ガチャのラインナップ更新を ID と交換pt の上でどう表すか（I2 の選択肢）。常設の交換対象、交換で消費する pt、既に持っているカードを交換したときの扱い
- 交換メダルを MVP で持つか。持たないなら GAC-04 の範囲も変わる。持つなら「余ったかけら」の定義と変換の RPC（I3）
- 割引単発の採否（I4）
- かけらを持つ単位（カードごとか、アイドルごとか）、サポートの上限解放の自動/手動と所持枚数・サポート強化pt の保存先、ピックアップのおまけかけら 50 の採否（I5）
- idol-support.md 1.8 の「開始時に全アイドルの R を所持」「かけら 100 で未所持を解放」「最初のプロデュースで SSR を 1 人選ぶ」を Uta で採るか（採ると R は常に重複になり、未所持解放の RPC が api-design.md にない）（I5）
- 排出テーブルのマスタ定義（表と列）と、カード 1 枚ごとの確率へのモデル（重み方式か、率 + 等分方式か）（I6）
- 10 連の確定枠の確率をマスタで持つか、内訳・ピックアップ率の振り替え方（I7）
- ガチャの乱数源、引く順序、履歴の粒度（I8）
- 同時実行の方針（I10）
- 天井を確かめる手段と、初期付与の量（I11）
