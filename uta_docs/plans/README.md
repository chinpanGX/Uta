# uta_docs/plans

実装計画の置き場。仕様（`uta_docs/wiki/`）が「何を作るか」を決め、実装計画は「どのファイルに何を書くか」を決める。実装は、この計画をもとに Sonnet のサブエージェントが行う（[ADR 0024](../wiki/decisions/0024-verification-first-reviews.md)。3 段の設計書は ADR 0017 から引き継ぐ）。品質は、この計画で決めた**動作検証**で担保する。

このページは書式の正。進め方は、計画を書くのが [uta-plan](../../.claude/skills/uta-plan/SKILL.md)、実装するのが [uta-implement](../../.claude/skills/uta-implement/SKILL.md)。

## 計画を書くとき

次のどれかに当たる変更は、実装の前に計画を書く。

- 複数のレイヤー（client / server / shared / masterdata）にまたがる
- 新しい型・サービスの IF・DTO・マスタの表・DB のテーブルを足す、または形を変える
- 実装を Sonnet のサブエージェントに任せる

1 ファイルで済む修正、誤字、設定の値の変更などは計画を書かずに直してよい。

## ファイル

- 名前: `YYYY-MM-DD-<件名>.md`（件名は英小文字とハイフン。例: `2026-11-01-gacha-draw.md`）
- レビューで何度でも書き換えてよい（raw と違う）。実装が終わったら `status: done` にして残す
- **書き換えは本文を直接直す。「読み替え」の節（「この節が本文と食い違ったら、この節が正」）を足さない。** レビューへの対応・方針の変更・コードレビューへの対応も同じ。変えた経緯はコミットメッセージに書く（[ADR 0018](../wiki/decisions/0018-change-log-from-git.md)）。実装担当は計画の一部の節しか読まないので、本文と食い違う節があると、古い本文のとおりに書いてしまう
- 2026-11-16 より前に `ready`・`in-progress` になった計画は、旧い書式（5章「テスト」・読み替えの節）のままでよい（[ADR 0024](../wiki/decisions/0024-verification-first-reviews.md)）

先頭に frontmatter を置く:

```
---
title: 実装計画: <件名>
status: draft | ready | in-progress | done
updated: YYYY-MM-DD
spec: <仕様ページへの相対パス（複数なら並べる）>
---
```

- `draft`: 書いている途中、またはレビューで直している
- `ready`: 設計書のレビュー（`requesting-design-review`）を通った。実装に渡してよい
- `in-progress`: 実装している
- `done`: 実装が終わり、仕様とのズレを wiki に反映した

## 計画のブランチと PR（流れ）

計画は Markdown だけなので、worktree（Unity の Library 用）は使わない。実装の worktree は、計画が `main` に入ってから使う。

1. **`main` を最新にしてから、計画用のブランチを 1 つ切る**（`main` のチェックアウトで `git pull --ff-only origin main` → `git switch -c claude/plan-<件名> main`）。1 つの変更（例: 順 7）の計画は、複数本でも同じブランチに書く
2. 計画を `status: draft` で書く。先頭に「この計画で決めたこと」と「ユーザーの確認が要ること」を置き、ユーザーはそこだけ読めば判断できるようにする。複数本なら、全体の順番と関係を 1 ページ（索引の計画）にまとめる
3. 設計書のレビューを回し、ユーザーの確認が取れたら `status: ready` にする
4. **`ready` にしたら、必ず `main` 向けに PR を作る**（docs だけの PR）。マージはユーザーが行う
5. マージされたら、各計画を固定の worktree（`tools/worktree-pool.sh start`）で実装する。実装の PR は計画ごとに分ける。実装が終わったら `status: done`

## 書くこと

基準は **Zero-Decision Rule**: この計画と、リンクした仕様・ADR だけを読んだ実装担当（Sonnet）が、**設計判断を一つもせずに**実装できること。DB の形、API のシグネチャ、依存の追加、新しい境界の扱いを、実装担当に選ばせない。
（egm の Implementation Readiness Standard による。[google/elephant-goldfish-model](https://github.com/google/elephant-goldfish-model)、Apache-2.0）

### 1. 目的と前提

- 何を実装するか（1〜3 文）。仕様は書き写さず、仕様ページの節へリンクする
- 関係する ADR
- この計画で**決めないこと**（範囲外。後の計画に回すもの）

### 2. 触るファイル

ファイルごとに **作成 / 変更 / 削除** を付けて並べる。

| 操作 | パス | 中身 |
|---|---|---|
| 作成 | `shared/Uta.Shared.Domain/Gacha/GachaTable.cs` | 排出テーブルの型 |
| 変更 | `server/...` | ... |

（表の行は例）

### 3. 型とシグネチャ

足す・変える型、メソッド、DTO、マスタの列、DB のテーブルを、名前・型・取りうる値まで書く。コードで書いたほうが早いものはコードで書いてよい（C# のバージョンは置き場所のフォルダの `.editorconfig` に合わせる）。

### 4. タスク

実装担当に 1 回で渡す単位に分ける。タスクごとに:

- 触るファイル（2 の表の行）
- 手順（何をどう変えるか。「〜を整える」ではなく「〜に〜を足す」）
- 境界の扱い（0 件、上限、失敗、重複した要求）
- 参照する 3章の節（例: 「参照: 3.2・3.4」）。実装担当は、ここに挙げた節しか読まない
- 終わったことの確かめ方: 5章の動作検証の、このタスクの行

**各タスクが終わったとき、ビルドとテストが通る状態にする。** 途中で壊れたままのタスクを作らない。

タスクの本文は、その節だけを読んで書ける形にする。「3章のとおり」「前のタスクと同じ」で済ませず、参照する節を挙げる。

### 5. 動作検証

品質の担保の中心（[ADR 0024](../wiki/decisions/0024-verification-first-reviews.md)）。計画を書く段階で決め、実装担当と進行役が**実行して**確かめる。コマンドは CLAUDE.md の「ビルド・テスト・実行」にあるものだけを書く。

**5.1 タスクごとの確かめ方**: タスクごとに、実行するコマンドと、期待する結果（通る件数・失敗 0・出力・終了コード）を書く。「目で見て確かめる」だけの確かめ方は書かない。

| タスク | コマンド | 期待する結果 |
|---|---|---|
| 1 | `dotnet test --project shared/Uta.Shared.Domain.Tests` | 失敗 0。`GachaTableTests` の 6 件が通る |

（表の行は例）

レイヤーごとの動作検証:

| レイヤー | 使うもの |
|---|---|
| shared | `dotnet test --project shared/Uta.Shared.Domain.Tests` |
| server | `dotnet test --project server/Uta.Server.Tests`（結合テストを含む。Docker が要る） |
| client | `unity recompile`、EditMode のテスト、**PlayMode のテスト**（`Assets/Tests/PlayMode`。回し方は CLAUDE.md）。画面・遷移・通信を触るタスクは PlayMode のテストで確かめる |

client の PlayMode のテストは、画面・遷移・通信を触るタスクで必須（基盤は [2026-11-16-client-playmode-tests.md](2026-11-16-client-playmode-tests.md)）。サーバーが要るテストは `[Category("Server")]` にし、5.1 の期待する結果に、ローカルのサーバーを上げることを書く。

**5.2 足すテストケース**: 正常系と境界ごとに並べる（テスト名は `Method_Condition_Result` の形でよい）。どのタスクで足すかを添える。

**5.3 受け入れ**: 全部のタスクが終わった後に、進行役が回すもの。全体のビルド（`dotnet build Uta.slnx`）と、触ったレイヤーのテスト全部。client を触る計画は、Editor で遊べることを確かめる手順（サーバーの起動 → Play → どこを押すと何が出るか）も書く。PlayMode のテストで確かめられない分は、ユーザーに頼む手順として書く。コードレビューは、受け入れが通ってから出す。

## 実装担当が守ること

- 計画の全文は読まない。読むのは「この計画で決めたこと」・1章・担当のタスク・そのタスクが挙げた 3章の節・5章のそのタスクの行
- タスクの動作検証を自分で回し、結果（コマンドと件数）を報告に書く
- 計画に書かれていない設計判断に出会ったら、自分で決めずに止まり、何が決まっていないかを報告する。計画を直してから続ける
- 計画と違うことをしたくなったら、理由を添えて報告する。黙って変えない
