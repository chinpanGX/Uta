# 実装可能性のチェックリスト

このページ（と関係するページ）だけを読んだ人が、**設計判断をせずに**実装を始められるかを見る。あなたは、このページをもとに明日コードを書く担当者として読む。
根拠: CLAUDE.md の「実装方針」「実装前のルール」、[repository-layout.md](../../../../uta_docs/wiki/architecture/repository-layout.md)、[api-design.md](../../../../uta_docs/wiki/architecture/api-design.md)、[masterdata-pipeline.md](../../../../uta_docs/wiki/architecture/masterdata-pipeline.md)、[lesson-domain-types.md](../../../../uta_docs/wiki/architecture/lesson-domain-types.md)。
egm の implementation_readiness・comprehension の観点を Uta 向けにまとめたもの。

**この観点は、実装を担当するモデル（Sonnet）で回す。** Uta は設計書の段階で実装の中身まで決め、コーディングは Sonnet のサブエージェントに任せることを目指している。あなた自身がその実装担当だと考えて読む。

**判断の基準:** 「どこに、何を、どう書くか」がこの文書で分かるか。分からず自分で決めるしかない箇所が、指摘になる。ただし、それが「未決事項」に挙がっているなら、穴ではなく決める順番の問題として扱う（その未決事項を決めないと実装に入れない、と書く）。

**対象が実装計画（`uta_docs/plans/`）なら、基準は一段上がる。** 下の「実装計画のとき」を全部確かめる。仕様ページなら「決まっていないと書けないもの」までを見る。

**段階に合わせる:** 叩き台（`status: draft` で中身が箇条書き）なら、全部がそろっていないのは当然。そのときは「実装に入る前に決める必要があるもの」の一覧として返す。

## 初めて読む人に分かるか

- [ ] 冒頭で、このページが何を決めるページか・何のためか分かるか
- [ ] 説明なしに使っている用語・略語がないか（glossary にあるならリンクがあるか）
- [ ] 前提にしている知識が、どのページにあるか示されているか

## 決まっていないと書けないもの

- [ ] **置き場所**: どの層・どのアセンブリ・どのフォルダに置くか（`shared/Uta.Domain`・`Uta.Shared`・`server/`・`client/uta/`・`masterdata/`）
- [ ] **データの形**: 型・フィールド・取りうる値の範囲・初期値。マスタなら列と型（int / long / string / bool / enum）、クライアントに出すかサーバーだけか
- [ ] **計算式**: 入力・出力・丸め方（切り捨て / 四捨五入）・上限と下限・整数で表せるか
- [ ] **処理の順番**: 状態がどう変わるか、どの順で処理するか、同時に起きたときの優先
- [ ] **境界の扱い**: 0 件・上限ちょうど・上限を超える・途中で失敗する・同じ要求が 2 回来る（冪等性）
- [ ] **サーバーとクライアントの分担**: どこで判定し、どこで確定するか。クライアントが予測表示するなら、何を使って予測するか
- [ ] **通信**: サービスの IF・DTO・エラーの返し方が決まっているか（api-design.md・server-foundation.md にそろうか）
- [ ] **乱数**: 乱数を使うなら、何回・どの順で引くか（同じシードで同じ結果になる順番か）
- [ ] **永続化**: 何を、どの単位で保存するか（ADR 0010）

## 作業として進められるか

- [ ] 実装の段階（フェーズ）があるなら、各段階が終わったときに動く・確かめられる状態になっているか
- [ ] 完了条件が、確かめられる形で書かれているか（「〜できる」が何で確かめられるか）
- [ ] 確かめ方（テスト）に書いたコマンドが CLAUDE.md の「ビルド・テスト・実行」に実在するか。Unity・実機でしか確かめられないものが、そうと分かるか
- [ ] 別のページの決定を待つ部分があるなら、それがどのページのどの未決事項か分かるか

## 実装計画のとき

基準は [plans/README.md](../../../../uta_docs/plans/README.md) の **Zero-Decision Rule**: この計画とリンクした仕様・ADR だけで、**設計判断を一つもせずに**実装できるか。あなたが「ここは自分で決めるしかない」と感じた箇所は、全部指摘になる。
（egm の Implementation Readiness Standard による）

- [ ] plans/README.md の「書くこと」の節（目的と前提・触るファイル・型とシグネチャ・タスク・テスト・未決事項）がそろっているか
- [ ] 触るファイルの全部に **作成 / 変更 / 削除** が付いているか（付いていなければ、ファイルごとではなく 1 件の Important として指摘する）
- [ ] 「変更」「削除」のファイルが実在するか（「作成」のファイルが無いのは当然なので指摘しない）
- [ ] 型・メソッド・DTO・マスタの列・DB のテーブルが、名前・型・取りうる値まで決まっているか。シグネチャを実装担当に選ばせていないか
- [ ] 各タスクの手順が、「〜を整える」「〜を対応する」のような要約でなく、何をどう変えるかになっているか
- [ ] 依存（パッケージ・サブモジュール・アセンブリの参照）の追加を、実装担当に選ばせていないか
- [ ] 各タスクが終わったとき、ビルドとテストが通る状態になるか。壊れたまま次のタスクに渡す区切りがないか
- [ ] タスクの大きさが、1 回のサブエージェントで終わる程度か（大きすぎるなら分け方を提案する）
- [ ] テストケースが正常系と境界ごとに挙がっていて、何を確かめれば終わりかが分かるか
- [ ] 計画が仕様を書き写さず、仕様ページの節へリンクしているか。計画と仕様が食い違っていないか
- [ ] 「未決事項」が空か。空でないなら、判定は「直せば」以下にする

判定の「このページで次に進めるか」は、実装計画では**「このまま実装担当に渡せるか」**として答える。

## 既にあるコードを説明するページのとき

対象が今あるコードの説明（例: [lesson-domain-types.md](../../../../uta_docs/wiki/architecture/lesson-domain-types.md) と `shared/Uta.Domain/`）なら、**この文書だけで、同じ振る舞いのコードを書き直せるか**を見る（egm の Re-Implementation Standard による）。

- [ ] 外から見える約束（シグネチャ、型、既定値、エラーの返し方、副作用）が書かれているか
- [ ] 振る舞いの決まり（計算、検証、状態の移り方、境界の扱い）が書かれているか
- [ ] 書かなくてよいもの（ループ、変数名、private の補助メソッド、外から見えない内部の構造）にまで降りていないか
