# 設計の批評のチェックリスト

設計そのものを疑ってかかる。根拠のない前提、扱われていないリスク、必要のない複雑さを探し、もっと単純にできないかを問う。
根拠: CLAUDE.md の「プロジェクト概要」（技術先行の個人開発。育成・ガチャの基礎部分）と「実装方針」、[game-spec.md](../../../../uta_docs/wiki/overview/game-spec.md) の MVP 範囲、[ADR](../../../../uta_docs/wiki/decisions)。
egm の design_critic・zoom_out の観点を Uta 向けにまとめたもの。

**Uta の前提:** 個人開発で、目的はゲームシステムの基礎部分を作ることと Unity 7 を早く触ること。運用規模の大きなサービスを前提にした仕組み（大量アクセス、複数チーム、細かい権限）は、要るという根拠がなければ過剰と見る。

**批評は代案とセットにする。** 「複雑すぎる」だけでなく、何を削れば・何に置き換えれば単純になるかを書く。ADR で決まった技術を変える代案は「ADR の見直しの提案」に分ける。

## 根拠のない前提

- [ ] 外部のもの（Unity 7 の機能、MagicOnion・MasterMemory・ライブラリの振る舞い、Cloud Run・Cloud SQL の制約）について、確かめていない前提を事実として書いていないか。Unity 7 はアルファ版（`7000.0.0a12`）なので、特に疑う
- [ ] 性能・容量・回数について、数字の根拠があるか
- [ ] 参考作品の構造を、Uta でも同じでよい理由なしに持ち込んでいないか

## 扱われていないリスク

- [ ] 不正: クライアントを改造されたときに、結果をごまかせる経路がないか（サーバー権威）
- [ ] 失敗: 通信が途中で切れた・同じ要求が 2 回届いた・サーバーが落ちたときに、所持品や育成の状態が壊れないか
- [ ] 変更: マスタの値や仕様を後から変えたとき、保存済みのデータ・配布済みのクライアントと食い違わないか（強制アップデートは実装しないので、古いアプリのまま接続されても壊れないか）
- [ ] iOS（IL2CPP / AOT）・モバイル実機で動かない設計になっていないか
- [ ] 1 か所が詰まると全体が止まる作りになっていないか

## 必要のない複雑さ（YAGNI）

- [ ] 今の MVP に要らない機能・設定・拡張点を入れていないか（「将来〜するかもしれないので」）
- [ ] 問題が起きていないのに、キャッシュ・分割・非同期のキューなどを入れていないか
- [ ] 抽象化の層が、差し替える相手が 1 つしかないのに増えていないか
- [ ] 既にあるもの（`shared/` の型、`external/` の共通基盤、ほかのページで決めた仕組み）で足りるのに、新しく作ろうとしていないか。コードを検索して確かめる
- [ ] 設計書が実装の細部（変数名、ループ、ヘルパー関数）に降りすぎて、構造・データの流れ・責務の分け方が見えなくなっていないか。**ただし実装計画（`uta_docs/plans/`）は、シグネチャや手順まで書くのが役目なので、細かさそのものは指摘しない**。見るのは、細部に埋もれて構造の判断が抜けていないか

## 筋の良さ

- [ ] 設計が、解きたい問題そのものに向いているか。症状を抑えるだけになっていないか
- [ ] 後で広げるときに作り直しが要る行き止まりになっていないか（逆に、行き止まりを避けるために今要らない仕組みを入れていないか）
- [ ] もっと単純な案があるなら、それと比べて今の案を選ぶ理由が書かれているか
