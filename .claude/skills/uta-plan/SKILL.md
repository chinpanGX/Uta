# 実装計画を書く（Uta 版）

[google/elephant-goldfish-model](https://github.com/google/elephant-goldfish-model) v0.1.0 の `egm-brainstorm`・`egm-draft`・`egm-resolve`・`egm-review-loop`（Apache-2.0、[LICENSE-egm](../requesting-design-review/LICENSE-egm)）の考え方を、Uta の 3 段の設計書に合わせて手順にした。

| 取り入れたもの | やめたもの |
|---|---|
| 書く前に弱点を洗う（Default to Stress-Testing） | 節ごとの承認（判断は計画の先頭の 2 節に集める） |
| 判断が割れるものはユーザーが決める（Owner Decides） | 推奨を付けない決まり（Uta では推奨を付ける） |
| 書き終えてからの自己点検（Zoom Out Standard） | `concepts_brief.md`・`design_draft.md` の中間ファイル（計画のファイルに直接書く） |
| 指摘の裁定（Contest は根拠が要る） | レビューの報告を別の文書にまとめ直す手順 |

**役割**: このセッションが Elephant（経緯を覚えていて、書いて、指摘を裁定する）。レビュー担当の Goldfish は経緯を持たない。**経緯はセッションと一緒に消えるので、残すべき判断は計画のファイルに書く。** 書式の正は [plans/README.md](../../../uta_docs/plans/README.md)。ここに書式は書かない。

## 手順

### 1. 計画が要るかを決める

[plans/README.md](../../../uta_docs/plans/README.md)「計画を書くとき」に当たらなければ、計画を書かずに直して終わる。当たるなら、`main` のチェックアウトで `git switch -c claude/plan-<件名> main`（worktree は使わない）。

### 2. 文脈を集める

書く前に読む。推測で埋めない。

- `uta_docs/wiki/index.md` → 仕様（`systems/`・`overview/`）→ 実装設計書（`architecture/`。何の正かは `architecture/README.md`）→ 関係する ADR
- **触る予定のコードを実物で読む**。シグネチャ・ファイルのパス・既にある部品は、wiki の記述ではなくコードで確かめる
- 前の計画（`uta_docs/plans/`）の実装メモ。同じ落とし穴を書き写すため

広く探す必要があるときは Explore に任せ、結論だけ受け取る。

**段が足りないときは先に戻る**（[ADR 0017](../../../uta_docs/wiki/decisions/0017-spec-design-plan-stages.md)）。

- ゲームのルールや値が決まっていない → `systems/` を先に書く
- 層・型・RPC・テーブルの形が決まっていない → `architecture/` を先に書く
- 技術選定・方針の変更が含まれる → ADR を先に起票する

### 3. 書く前に弱点を洗う

作ると決める前に、次を自分に問う。答えは、計画に関わるものだけ先頭の節に書く。

- 解こうとしている問題は何か。計画が扱う範囲より小さい変更で解けないか
- 一番弱い前提はどれか。外れたらどこまで書き直しになるか
- 動くと確かめていないもの（Unity 7 の早期版・AOT・パッケージ）はどれか。スパイクのタスクを先頭に置き、「止まる条件」を書く
- 既にある部品で足りないか

### 4. 判断を分ける

| 種類 | 扱い |
|---|---|
| 答えが 1 つに決まる（命名・ファイルの置き場・書式） | 自分で決める。聞かない |
| 答えが割れる（データの形・境界・依存・見た目の値） | 「ユーザーの確認が要ること」に書く。案は 3 つまで。案ごとに仕組み・得失・**どんな条件で失敗するか**を書き、推奨を 1 つ付ける |
| ADR に反する、未決事項を決める | 自分で決めない。確認に書き、ADR との関係を添える |
| 指定が足りず先へ進めない | その場で `AskUserQuestion` で聞く。それ以外は下書きを進め、まとめて聞く |

### 5. 下書きを書く

`status: draft` で、書式どおりに書く。

- 先頭の「この計画で決めたこと」「ユーザーの確認が要ること」だけで、ユーザーが判断できるように書く
- 各タスクの終わりでビルドとテストが通るように切る。実装担当は 1 タスク分の文脈しか持たない
- 本数が増えるなら分け、順番と関係を索引の計画にまとめる（例: [client/ の画面 索引](../../../uta_docs/plans/2026-11-07-client-screens-index.md)）
- 計画を書く途中で決めた設計のうち、ほかの機能からも引くものは `architecture/` にも書く

### 6. 自己点検する

レビューに出す前に、次を見て直す（Goldfish を出すより安い）。

- **範囲**: 根本の問題から外れた変更はないか。「将来のため」の抽象・設定・拡張点はないか（YAGNI）。再利用できる部品を作り直していないか
- **Zero-Decision**: 実装担当に判断を残す言葉がないか

  ```bash
  grep -nE '適切に|必要に応じて|など適宜|うまく|よしなに|検討する|整える' <計画のファイル>
  ```

- **実在**: 書いたパス・型・コマンドが実在するか（作成するものを除く）。コマンドは CLAUDE.md「ビルド・テスト・実行」にあるものだけ
- **Lint**: `python -I .claude/skills/linting-wiki/lint_wiki.py`

### 7. ユーザーの判断をもらう

確認の節が残っているなら、レビューの前に聞く（`AskUserQuestion`、または計画へのリンクと推奨を添えて）。答えが変わると Goldfish の結果が無駄になるため。答えは「この計画で決めたこと」へ移し、日付と「ユーザーの判断」を添える。

### 8. レビューと裁定を回す

[requesting-design-review](../requesting-design-review/SKILL.md) で 3 つの観点を出し、同じスキルの「5. 指摘に対応する」に従って裁定する。

- 2 回目は Critical か Important が出た観点だけ、`[FOCUS]` に直した節を挙げて出す。スキルは呼び直さない
- **終わる条件**: 実装可能性の判定が「はい」で、Critical・Important と未決事項が残っていないこと
- 2 回目でも同じ指摘が残るなら、3 回目を出す前にユーザーに相談する

### 9. ready にして PR に出す

1. `status: ready` にし、`updated` を更新する。索引があれば状態を直す
2. ユーザーの承認を取り、`main` 向けの PR を作る（`gh pr create`。docs だけ）。マージはユーザーが行う
3. ここが区切り。続けず、実装は新しいセッションで [uta-implement](../uta-implement/SKILL.md) を使うよう提案する（`start_session`。ブリーフには計画のパスを書く）

## してはいけないこと

- 実装担当に「いい感じに」判断を残す
- 未決事項を、レビューの指摘に従って勝手に決める
- コードを読まずにシグネチャを書く
- 確かめていないビルド・テストの結果を「通る」と書く
- ユーザーの確認が残ったまま `ready` にする
