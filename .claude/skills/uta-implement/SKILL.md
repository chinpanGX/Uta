# 実装計画を実装する（Uta 版）

実装担当も Goldfish と同じく経緯を持たない。**計画だけを読んで書けるなら計画は足りている。止まったら足りないのは計画なので、実装担当に決めさせず、計画を直す。**

**役割**: このセッションは進行役。コードは書かず、大きな差分も読まない。タスクを渡し、確かめ、記録し、コミットする。

進み具合は計画の「実装メモ」（[plans/README.md](../../../uta_docs/plans/README.md)）に書く。セッションが変わっても、そこから再開できるようにする。

## 手順

### 1. 始める前に確かめる

- 計画が `status: ready`（再開なら `in-progress`）で、`main` か前提のブランチに入っている。`draft` なら実装に入らず [uta-plan](../uta-plan/SKILL.md) に戻す
- 計画の 1章の前提（前の計画・マージ済みの PR）が満たされている。満たされていなければ止まって報告する
- ブランチ: 固定の worktree で `tools/worktree-pool.sh start <番号> <新ブランチ> [base]`。前提のタスクが未マージなら積み PR にする（CLAUDE.md「Git」）。新しい worktree は作らない
- 計画を `status: in-progress` にし、実装メモの表がなければ足す
- 再開のときは、実装メモで終わったタスクを飛ばす

### 2. タスクを 1 つずつ渡す

タスクごとに、専用の実装担当 `uta-implementer`（`.claude/agents/uta-implementer.md`）を新しく 1 つ出す。並行しない（同じファイルに触るため。計画が並行してよいと書いたときだけ並べる）。

守ること・読むもの・報告の形式・モデル・effort・使えるツールはエージェントの定義にあるので、依頼文には**どのタスクか**だけを書く。会話の経緯は書かない。

```
Agent:
  subagent_type: uta-implementer
  description: "実装: [計画の件名] タスク [N]"
  prompt: |
    計画: [計画のパス]
    担当: タスク [N] だけ
    作業フォルダ: [worktree のパス]
```

- `model`・`effort` は渡さない（定義の値は Sonnet・medium）。ユーザーが別の指定をしたときだけ渡す
- `uta-implementer` が使えるエージェントの一覧にないときは、セッションを開き直すようユーザーに頼む。`general-purpose` で代わりに出さない（モデルの指定と止まる決まりが外れる）

### 3. 確かめて記録する

実装担当の報告をそのまま信じない。

1. 計画のタスクの「終わったことの確かめ方」のコマンドを、進行役が実行する（CLAUDE.md「ビルド・テスト・実行」にあるものだけ）
2. `git status --short` と `git diff --stat` で、計画の範囲外のファイルに触っていないか見る
3. 通ったらコミットする（日本語。何を変えたかと決めたこと）。`uta-implement` を頼まれたことが、タスクごとのコミットの依頼を含む。push はしない
4. 実装メモの表に、タスク・コミット・ズレを 1 行足す

Unity や実機でしか確かめられないものは、確認できていないと実装メモに書き、ユーザーに実行を頼む。

### 4. 止まったとき

| 理由 | すること |
|---|---|
| 計画に書き漏れた。答えは仕様・実装設計書から決まる | 計画を直し、同じタスクを出し直す |
| 設計判断が要る | ユーザーに確認する（案と推奨を添える）。答えを計画に書き、出し直す |
| 計画の前提が崩れた（スパイクが失敗した、パッケージが動かないなど） | 後のタスクに進まない。ユーザーに報告する |
| ADR に反する | 実装を止め、ADR を見直す提案としてユーザーに確認する |

- 実装担当の修正は、前の担当に続けさせる（`SendMessage`）。文脈が要らないなら新しく出す
- 型やシグネチャを大きく変えたら、変えた節を [requesting-design-review](../requesting-design-review/SKILL.md) の実装可能性の観点に出し直す
- 同じタスクで 2 回止まったら、3 回目を出す前にユーザーに相談する

### 5. コードレビュー

全タスクが終わったら、[requesting-code-review](../requesting-code-review/SKILL.md) でレイヤーごとに出す。

- 既定は計画ごとに 1 回。スパイクの直後や、通信の契約・DB の形を変えるタスクの後は、途中でも出す
- 直すのも実装担当に任せる。Critical・Important を直し、Minor は実装メモに残す
- 直したら指摘があったレイヤーだけ出し直す。2 回目でも同じ指摘が残るならユーザーに相談する

### 6. ズレを wiki に反映する

実装メモの「ズレ」の列を全部見て、CLAUDE.md の「実装前のルール」の 8 に従う。

- 実装設計書（`architecture/`）を直す。実装で決まった細部も書き戻す
- ゲームの挙動が変わったときだけ、仕様（`systems/`）も直す
- 計画の「触るファイル」の表に wiki の更新があれば、それも済ませる
- `python -I .claude/skills/linting-wiki/lint_wiki.py`

**ズレを計画の中だけに残さない。** 次に読まれるのは wiki。

### 7. 終える

1. 計画を `status: done` にし、`updated` を更新する。索引があれば状態を直す
2. 全体のビルドとテストの結果を確かめる。未確認のものはそう書く
3. push して PR を作る。確認を取らずに必ず行う。マージはユーザーが行う。本文に計画へのリンク、確認できていないこと、前提の PR を書く。実装の PR は計画ごとに分ける
4. ここが区切り。次の計画は新しいセッションで始めるよう提案する（`start_session`）

## してはいけないこと

- 進行役がコードを書く、大きな差分を読み込む
- 計画にない判断を、実装担当に決めさせる、進行役が黙って決める
- 実装担当の「通りました」だけで次へ進む
- Unity で確かめていないものを確かめたと書く
- ビルドやテストが壊れたまま次のタスクへ進む
- `git commit --no-verify` などで確認を飛ばす
