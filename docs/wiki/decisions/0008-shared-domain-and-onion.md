# ADR 0008: ドメイン層をクライアント・サーバーで共有し、クライアントはオニオンアーキテクチャにする

## 状況

クライアント・サーバーとも C# で、`shared/` で型を共有できる。[lesson-card.md](../systems/lesson-card.md) 15.7 は「同じシードと操作列で、クライアントとサーバーの結果が完全に一致する」ことを完了条件にしている。計算ロジックを両側で二重に書くと、食い違いのリスクが大きく、個人開発では保守も重い。

一方、[CLAUDE.md](../../../CLAUDE.md) は「クライアントは表示と入力のみ」、[produce.md](../systems/produce.md) 10章は「クライアントは乱数を持たない」としている。

## 決定

- **ドメイン層 `shared/Uta.Domain` を共有する**。中身は純粋なゲームルール（計算式、状態遷移、検証、値オブジェクト、enum、ID 型）
  - netstandard2.1、C# 9。UnityEngine・MasterMemory・生成物に依存しない
  - `float` / `double` を使わない。乱数は `IRandom` を注入し、決定的な疑似乱数を使う。`System.Random` は使わない
  - マスタの値は引数または小さなインターフェース越しに受け取る。`[ServerOnly]` の列には依存しない
- **通信契約は `shared/Uta.Shared`** に分ける（サービスIF・DTO・エラーコード）
- **クライアントはオニオンアーキテクチャ**にする。`Domain` → `Application` → `Infrastructure` / `Presentation` → `Bootstrap`。層ごとに asmdef を分け、依存の向きをコンパイルで強制する。`Application` は UnityEngine に依存しない
- **サーバーは同じ層の考え方を、1プロジェクト内のフォルダと名前空間で表す**。依存の向きはアーキテクチャテストで守る（基盤と同じ方針）
- **サーバー権威は変えない**。結果の確定は常にサーバー
- **クライアントは `Uta.Domain` を、使用可否の判定と予測の表示まで使う。クライアントにはシードを渡さない**（2026-10-27 に確定）。乱数が絡む結果（ドローなど）は予測しない。「同じシードと操作列で結果が一致する」ことは、本番のクライアントではなく CI のテストで確かめる
- **DTO ↔ Domain のマッピングは Infrastructure に閉じる**（2026-10-27 に確定）。DTO は enum とプリミティブ型で組み、マッピングを薄く保つ
- **クライアントの `Application` は UniTask を参照してよい**（[ADR 0009](0009-client-stack.md)）。そのため asmdef の `noEngineReferences` は使わず、「UnityEngine の API を使わない」ルールをレビューまたはアナライザーで守る。`Uta.Domain` は同期処理だけにする
- **固有の知識は共通のドメインに入れず、各側の外側の層に置く**。サーバー固有（抽選、天井、シード生成、レンタル候補の決定、報酬付与）はサーバーの `Domain/`、クライアント固有（表示用の整形、演出、UI の状態）はクライアントの `Application` / `Presentation`。共通の型を各側のエンティティが包む（合成）形にし、継承・`partial` は使わない（[repository-layout.md](../architecture/repository-layout.md) 6.1）

詳細は [architecture/repository-layout.md](../architecture/repository-layout.md)。

## 理由

- 計算ロジックの二重実装を避け、クライアントとサーバーの結果の一致をテストで保証できる
- 整数演算と決定的な乱数に絞れば、IL2CPP と .NET 10 で同じ結果になる
- オニオンにすると、`Domain` / `Application` を Unity とマスタの形式から独立させられ、テストしやすい。asmdef で依存の違反をコンパイル時に検出できる

## 検討した代替案

- 案A: 両側に別々に実装する。食い違いのリスクが高く、工数が二重になるため不採用
- 案B: ロジックはサーバーにだけ置き、クライアントは表示のみ。結果の予測や使用可否の判定に毎回通信が要り、体験が悪くなる。ただし CLAUDE.md の記述には最も近い
- 案C: クライアントを層に分けず、MonoBehaviour 中心の構成にする。小さくは済むが、ロジックのテストと共有が難しい

## 影響・リスク

- クライアントが `Domain` を使う範囲を「判定と予測の表示まで」にしたため、CLAUDE.md の「クライアントは表示と入力のみ」と、[produce.md](../systems/produce.md) 10章を更新した（2026-10-27）。結果の先行表示（シードをクライアントに渡す案）は、山札の引きを先読みする不正を防げないため採らない
- `shared/` は C# 9 の制約を受ける（Unity 7 で C# 14 が使えると確認できたら見直す。[ADR 0006](0006-adopt-unity-7-early.md)）
- `Application` の UnityEngine 非依存を、コンパイルで強制できない（UniTask を参照するため）
- DTO と Domain の型のマッピングのコードが `Infrastructure` に要る。代替の「`Application` が DTO を参照してよい」形は、API の変更が画面まで波及するため採らない
- 古いクライアントの計算式がサーバーの最新式とずれうる。表示用の予測はずれを許容し、確定はサーバーのレスポンスで行う
- 層ごとの asmdef とアーキテクチャテストの整備コストがある
- 「クライアント固有」に置いたルールが結果に影響し始めたら、共通へ移す必要がある（別々に実装すると食い違う）

## 見直す条件

- クライアントとサーバーの結果の一致が、IL2CPP と .NET 10 の差で保てないと分かったとき
- オニオンの層分けが個人開発では重すぎると感じたとき（層を減らす）
- Unity 7 の CoreCLR 対応で `shared/` の制約（C# 9）が変わったとき
